# v1.13.0

> 릴리스 날짜: 2026-08-21

`dev-monitor` 의 **Monitor 재사용이 처음부터 동작한 적이 없었다.** 중복 기동 방지가 이 스킬의 존재
이유인데 그 축이 통째로 죽어 있었다. 그걸 고치고, `harness-dev` 가 무엇인지 잘못 적혀 있던 설명
5곳을 실물에 맞춘다. 사용 가이드를 새로 넣는다.

---

## ⚠️ 업데이트하면 달라지는 것

**상태 파일 스키마가 바뀐다** — `~/.claude/dev-monitor/port-<port>.state.json`.
`monitor_task_id` 와 `monitor_pid_file` 이 추가되고, `monitor_pid` 는 이제 **진짜 PID** 다.

1.1.0 이전 파일은 자동으로 stale 처리되므로 **손댈 필요 없다.** 그냥 다시 실행하면 된다.
값이 숫자가 아니면 구스키마로 보고 생존 판정과 `kill` 을 건너뛴다.

**`harness-dev` 는 "스킬 집필 도구"가 아니다.** README·AGENTS.md·매니페스트에 그렇게 적혀 있었지만
실제 SKILL.md 는 **3-에이전트(Planner→Generator→Evaluator) 자율 개발 워크플로**다. 스킬 집필 얘기는
한 줄도 없다. **동작은 그대로고 설명만 고쳤다** — 쓰던 방식을 바꿀 필요는 없다.

## 🐛 Fixed

- **`monitor_pid` 로는 `ps -p` 도 `kill` 도 되지 않았다** — `Monitor` 도구는 PID 가 아니라 task ID
  문자열(`"b1cgaqjgm"`)을 돌려주는데 스킬이 그것을 PID 로 취급했다. 결과적으로 Monitor 는 **항상
  "죽음"으로 판정**됐다. 재호출마다 Monitor 가 중복 등록됐고 `stop` 은 Monitor 를 못 죽였다.
  명령 첫 줄에 `echo $$` 를 넣어 래퍼 셸의 진짜 PID 를 pidfile 로 확보한다.

- **래퍼를 죽이면 `tail` 이 고아로 남았다** — `kill <래퍼>` 하면 자식 `tail` 이 PID 1 로
  재부모화되어 살아남는다. 재등록할 때마다 같은 로그를 붙든 `tail` 이 하나씩 쌓였다.
  종료 순서를 `pkill -P` → `kill` 로 못 박고 고아 청소를 넣었다.

- **서버와 Monitor 의 수명 차이가 명문화되지 않았다** — 근본 원인이 여기 있었다. 서버는 `nohup`
  이라 세션을 넘고 Monitor 는 못 넘는데, 둘을 같은 `ps -p` + `kill` 로 다루려 했다.

## 🔄 Changed

- **`harness-dev` 설명 5곳을 실물에 맞췄다** — `plugin.json`, `marketplace.json`, 루트 `README.md`
  2곳, 플러그인 `README.md`. `AGENTS.md` 의 "스킬 집필 도구"는 **"3-에이전트 하네스의 참조 구현"**
  으로 바꿨다. 그 섹션의 맥락(스킬 수정 시 참고할 근거)에서는 참조 구현이라는 의미가 맞다.

- **새 세션의 "서버 생존 + Monitor 죽음"은 정상 경로가 됐다** — 사고로 취급하지 않는다.
  서버만 재사용하고 Monitor 는 재등록한다.

## ✨ Added

- **`docs/guide/harness-devkit.md`** (342줄) — `project-conventions` 가이드와 같은 형식.
  두 스킬이 왜 한 플러그인인지, 3-에이전트가 무엇을 막는지, **같은 패턴을 쓰는 다른 스킬 4개와
  언제 갈리는지** 구분표, 자주 막히는 곳. 강제 수단이 문서뿐이라는 한계도 적었다.

## 기술 상세

### 왜 처음부터 동작하지 않았나

`Monitor` 도구의 반환값을 PID 로 가정한 것이 전부다. 실제 상태 파일을 열어 보면 바로 보인다.

```json
"server_pid": 46319,          ← 진짜 PID (숫자)
"monitor_pid": "b1cgaqjgm",   ← task ID (문자열)
```

`ps -p "b1cgaqjgm"` 는 항상 실패하고, 실패는 "프로세스 없음"으로 읽힌다. 그래서 Phase 0.5 의
재진입 판정이 **언제나 "Monitor 죽음"** 으로 떨어졌다. 조용한 실패다 — 에러가 안 나고 Monitor 가
하나 더 붙을 뿐이라 겉보기엔 정상이다.

계약이 문서 안에서도 갈라져 있었다. Phase 0.5 스키마는 `"monitor_pid": 12346` 이라고 숫자로 적어
놓았는데 Phase 7 출력 포맷만 `| Monitor ID |` 라고 써서 실물과 맞았다.

### `echo $$` 로 진짜 PID 를 확보한다

`Monitor` 도구가 PID 를 안 주므로 셸에게 직접 물었다.

```bash
echo $$ > ~/.claude/dev-monitor/port-8000.monitor.pid
tail -f /tmp/dev_server_8000.log | grep --line-buffered -E "..."
```

`$$` 는 파이프라인을 감싼 래퍼 셸의 PID 다. 셸이 살아 있으면 파이프라인도 살고, 세션이 끝나 Monitor
가 정리되면 그 PID 도 사라진다. **기존 설계 의도(`ps -p` · `kill`)를 그대로 살리면서 실제로 동작하는**
최소 변경이다. task ID 는 `monitor_task_id` 로 분리해 같은 세션의 `TaskStop` 에만 쓴다.

### 종료 순서가 뒤집혀 있었다

실측으로 확인한 것이다.

```
kill <래퍼>  먼저   → tail 이 PPID 1 로 재부모화되어 생존  ❌
pkill -P <래퍼> → kill <래퍼>  → 자식까지 정리됨  ✅
```

`pkill -f "tail -f ${LOG_PATH}"` 로 남은 고아를 청소한다. 로그 경로는 상태 파일에서 읽으므로 **이
스킬이 띄운 tail 만** 겨냥한다. 경로 없이 `pkill tail` 로 넓히면 사용자의 다른 tail 을 죽인다.

### 검증

| 대상 | 방법 | 결과 |
|---|---|---|
| pidfile 이 진짜 PID 를 담나 | 실제 프로세스 기동 후 `ps -p` | ✅ 통과 |
| `pkill -P` → `kill` 순서 | 자식 정리 후 잔여 프로세스 확인 | ✅ 고아 0건 |
| `kill` 만 했을 때 | 고아 발생 여부 | ⚠️ 재현됨 (그래서 순서를 못 박음) |
| mermaid 3개 | `@mermaid-js/mermaid-cli` 로 SVG 렌더 | ✅ 3/3 |
| 가이드 상대 링크 6개 | 실재 확인 | ✅ 6/6 |
| 매니페스트 정합성 | `scripts/validate-marketplace.sh` | ✅ 전 검사 통과 |

**통합 검증은 하지 않았다** — 아래 알려진 이슈 참조.

### 버전

`harness-devkit` 1.0.0 → **1.1.0**. 나머지 5개 플러그인은 유지. 마켓플레이스 `metadata.version`
1.12.0 → **1.13.0**. 상태 파일 스키마가 바뀌고 사용자가 체감하는 동작(중복 등록이 실제로 막힘)이
달라지므로 MINOR 다.

스킬 18개 · 플러그인 6개 유지. 이 저장소는 `package.json` / `app.json` 이 없는 플러그인
마켓플레이스라 Expo 빌드 번호는 해당 없음.

`dev-monitor/SKILL.md` 는 500줄이 되어 이 저장소에서 가장 긴 스킬이 됐다. AGENTS.md 의 500줄
목표는 지켰지만 여유가 없으므로, 다음에 커지면 `references/` 분리가 필요하다.

### 알려진 이슈

- **실기 통합 검증이 남아 있다.** pidfile 과 고아 정리는 실제 프로세스로 재현 확인했지만, 서버를
  띄워 Phase 0.5 → 5 → 8 을 한 바퀴 도는 확인은 하지 않았다. **핵심 회귀 테스트는
  `/harness-devkit:dev-monitor <port>` 를 두 번 연속 호출해 두 번째가 "기존 Monitor 재사용"으로
  빠지는지** 보는 것이다. 지금까지 그 경로는 한 번도 타지지 않았다.
- **강제 수단이 문서뿐이다.** `harness-devkit` 에는 스크립트도 훅도 없다. 8가지 기계적 제약도 하드
  게이트 2개도 실행 시점에 검사하는 코드가 아니라 SKILL.md 에 적힌 지시다. 규율이 깨지면 조용히
  깨지므로 `sprint_reports/` 를 사람이 열어 보는 것이 유일한 실질적 검증이다.
- **`harness-dev` 는 자동 트리거된다.** `disable-model-invocation` 이 없어 "복잡한 앱 만들어줘"
  류 문구로 의도치 않게 발화할 수 있다. Phase 0 이 기능 3개 이하면 일반 개발로 전환한다.
- **`docs/harness/` 는 여러 스킬이 공유하는 이름공간이다.** slug 격리 이전 산출물(`docs/harness/`
  바로 아래의 `progress.md`·`sprint_reports/`)이 남아 있으면 다른 프로젝트를 또 돌릴 때 덮어쓴다.
- Notion Tasks DB 매핑 불가 — 이 저장소는 Notion 을 상태 저장소로 쓰지 않는다.
