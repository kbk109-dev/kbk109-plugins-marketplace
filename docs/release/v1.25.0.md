# v1.25.0

> 릴리스 날짜: 2026-11-12

`harness-devkit` 2.1.0 — `harness-dev` 의 소요 시간을 줄이는 마이너 릴리스다. 안전장치(Generator/Evaluator 분리, 기본 `fail`, 증거 로그, 구현 전 TC 잠금, 한 번에 한 기능)는 그대로 두고, 판단이 필요 없는 일을 LLM 턴에서 스크립트로 옮겼다.

실제 실행 기록 1건(에픽 13 · 기능 132 · TC 2,140 · 활성 86시간)의 `PROGRESS.md` 시각을 집계한 결과 evaluator 32%, generator 30%, TC 작성·검토 20%, 에픽 종료 14% 였다. 이 비율이 변경 대상을 정한 근거다.

---

## ✨ Added

- **TC 러너 `run_tc.py`** — 확정 TC 의 `command` 를 실행해 `logs/<FID>/<n>.log` 와 `summary.json` 을 쓴다. TC 잠금이 맞을 때만 돌고, TC 마다 timeout 을 걸어 프로세스 그룹째 정리하며, Bash 도구의 10분 상한 전에 멈춰 `--resume` 으로 이어 간다. evaluator 가 TC 를 한 턴에 하나씩 돌리고 로그를 손으로 쓰던 일을 대체한다
- **`validate_harness_doc.py tc-review-prep`** — critic 호출 직전에 그 라운드가 볼 내용의 스냅샷을 남기고, 블록 해시로 직전 라운드 이후 바뀐 블록만 `reviews/tc-critic-r{N}.scope.md` 로 뽑는다
- **`harness_state.py log`** — 시각이 찍힌 `PROGRESS.md` 한 줄을 남긴다. 메인 에이전트가 쓰는 유일한 경로다
- **`tc-revise` 판정** — TC 의 모양·추적성이 깨졌으면 `harness_state.py` 가 `tc-critic` 대신 `tc-revise` 를 낸다. 코드로 잡을 수 있는 결함에 critic 라운드를 쓰지 않는다
- 4,000바이트를 넘는 TC 블록은 검증 결과의 `warnings` 로 알린다 (위반 아님)

## 🔄 Changed

- **제약 11 강화** — 새 `pass` 는 `logs/<FID>/summary.json` 이 "전부 돌려 전부 통과, 잠금 일치" 여야 한다 (`validate_feature_list.py --prev`). 이전에 pass 가 된 기능과 `TC.md` 가 없는 1.x 레이아웃은 대상이 아니다
- **evaluator 는 실행자에서 감사자로** — 통과한 TC 가 부르는 테스트가 `expected` 를 정말 단언하는지 확인하고 `파일:줄` 을 보고서에 남긴다. TC 규칙에는 "`command` 는 `expected` 를 종료 코드로 답한다" 를 더했고, 끝을 `|| true` 로 가린 명령은 `validate_harness_doc.py tc` 가 위반으로 잡는다
- **회귀 범위 축소** — 기능 평가의 회귀는 직접 의존 기능의 TC 와 PLAN `test` 1회다 (`run_tc.py --regression`). 확정 TC 전체는 에픽 종료 회귀(`--all --out _epic`)에서 돈다. 기능 사이의 파손이 그때 처음 드러날 수 있다
- **tc-critic 은 2라운드부터 바뀐 블록만 본다** — `MAX_ROUNDS = 2` 인데도 실측은 에픽당 3~11라운드였다. 새 critic 이 매번 전체를 처음부터 읽던 것이 원인이다
- **`PROGRESS.md` 는 메인만 한 줄씩 쓴다** — generator 는 끝 40줄과 의존 기능의 `notes/<FID>.md` 만 읽고, 작업 기록은 자기 `notes/<FID>.md` 에 쓴다. 540 KB 까지 커진 파일을 매 시작에 읽던 것을 없앤다
- 회귀·자가 점검·에픽 회귀의 로그는 `logs/_regression/` · `logs/_self/` · `logs/_epic/` 에만 쓰여 증거 자리(`logs/<FID>/`)와 섞이지 않는다

## 🐛 Fixed

- **잠금 뒤 TC 수정의 재검토 누락** — 2라운드를 넘긴 뒤 TC 를 고치면 상태 머신이 재검토 없이 `tc-lock` 을 냈다. 이제 리뷰 뒤에 내용 해시가 바뀌었으면 라운드 수와 무관하게 `tc-critic` 을 낸다. `tc-lock` 은 모양·추적성이 맞고 최신 리뷰가 PASS 이며 그 리뷰가 본 내용이 지금과 같을 때만 잠근다
- **`parse_tcs` 가 마지막 TC 의 명령을 덮어쓰던 문제** — TC 가 아닌 제목(`## 제외한 관점` 등) 아래의 `- command:` 줄이 마지막 TC 의 명령을 덮어썼다
- **`tc-writer` · `feature-planner` 가 검증 스크립트를 실행하지 못하던 문제** — 본문은 실행을 요구하는데 `tools` 에 `Bash` 가 없었다
- **에픽 종료 `/simplify` 순서** — 회귀 평가 뒤로 밀려 검증되지 않은 수정이 커밋될 수 있었다. 항상 회귀 평가 앞에서 한 번 돈다

## 기술 상세

### 버전

- `harness-devkit` 2.0.0 → 2.1.0, 마켓플레이스 `metadata.version` 1.24.1 → 1.25.0
- 사용자가 `--user-approved` 로 에스컬레이션의 남은 지적을 안고 TC 를 잠그는 경로는 유지된다 (면제되는 것은 critic 의 VERDICT 뿐이다)

### 검증

- `validate-marketplace.sh` 8개 검사 통과
- 2.1 스크립트 검증 71건 통과 — TC 러너의 잠금 확인·재개, `tc-lock` 의 리뷰 요구, `tc-revise` 라우팅, 변경 블록 검토 범위
- 파서와 검사를 실제 13개 에픽의 `TC.md` 에 돌려 새 규칙이 기존 산출물을 거부하지 않음을 확인했다

### 알려진 한계

- **소요 시간 단축 폭은 아직 측정하지 않았다.** 위 비율은 2.1 이전 실행의 기준선이고, 2.1 로 돈 실제 실행은 아직 없다
- generator 의 구현 시간과 테스트 실행 시간 자체는 이 변경으로 줄지 않는다. 기능 병렬 구현은 넣지 않았다
- 기계 제약 11개 중 코드가 시행하는 것은 8개다 (`plugins/harness-devkit/README.md` 참조)
