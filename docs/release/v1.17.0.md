# v1.17.0

> 릴리스 날짜: 2026-09-04

Notion 을 **플러그인이 전제하는 의존성에서 프로젝트가 선택하는 연동으로** 내린다.
`release-workflow`·`product-planning` 은 이제 Notion MCP 도구 이름을 하나도 모른다. 강제는
`project-conventions:init-agent-rules` 하나로 모은다 — 프로젝트 세팅 시 Notion 사용 여부를
묻고, 쓴다고 답하면 그 자리에서 Notion MCP 호출을 막는 훅과 토큰 기반 REST 클라이언트를
설치한다.

---

## ⚠️ 업데이트하면 달라지는 것

**5개 스킬이 더 이상 Notion MCP 도구 이름을 지시하지 않는다** —
`release-plan`·`release-impl`·`fix-plan-impl`·`main-branch-merge`·`create-prd`. 각 스킬은
Notion 이 필요한 지점마다 "이 프로젝트에 `.claude/rules/notion-api-only.md` 가 있으면 그
규칙(`.claude/scripts/notion_api.py`)을 따르고, 없으면 대체 경로로 빠진다"로 위임한다.
Notion MCP 가 이미 연결된 환경에서 지금까지 이 플러그인들이 동작해 왔다면, 업데이트 후에는
프로젝트에 `notion-api-only` 규칙을 설치해야 같은 동작을 계속 얻는다.

**`create-prd` 의 `compatibility: 'mcp: notion'` frontmatter 가 사라진다.** Notion 부모 페이지
입력이 "Notion 연동이 있는 프로젝트에서만 필수"로 낮아졌다 — 없으면 로컬
`docs/plan/PRD-{slug}.md` 완성만으로 끝난다.

**`main-branch-merge` Step 5 의 "Notion 문서 수정" 능력이 사실상 축소된다.** REST API 는 페이지
속성 갱신은 지원하지만 본문 문장 교체에 대응하는 호출이 없다 — 수정 실패는 이 스킬의 기존
정책("실패 시 리포트만, 블로킹하지 않음")으로 흡수된다.

**`project-conventions:init-agent-rules` 에 새 질문과 새 설치물이 생긴다.** Step 1.5 에서
"Notion 을 쓰는가"를 묻는다. 예로 답하면(`--notion-rule on`)
`.claude/scripts/notion_api.py`(REST 클라이언트) · `.claude/hooks/notion_mcp_gate.py`(차단
훅) · `.claude/settings.json` 의 `PreToolUse` 등록(기존 키는 보존하며 병합)이 추가된다.
기본값은 `off` — 아무것도 물어보지 않으면 지금까지와 동일하게 `git-branch-workflow` 규칙만
설치된다.

**`notion_mcp_gate.py` 는 탈출구가 없다.** 토큰을 구할 수 있는 프로젝트에서 Notion MCP 도구를
부르면 재시도해도 계속 막힌다. 이건 `harness-devkit` 의 훅과의 의도적 차이다 — 그 훅은
**플러그인 번들**이라 켜진 모든 프로젝트에서 발화하므로 AGENTS.md 의 "전역 훅은 재시도하면
통과해야 한다" 규칙을 따르지만, 이 훅은 사용자가 **그 프로젝트에서 명시적으로 옵트인**해야만
설치되므로 그 규칙의 적용 대상이 아니다. `NOTION_MCP_GATE=off` 로 그 프로젝트에서만 끌 수 있다.

## 기술 상세

### 왜 위임 패턴인가

첫 설계안은 5개 스킬이 `notion_api.py` 서브커맨드를 직접 지시하는 방식이었다. 이 방식은
`${CLAUDE_PLUGIN_ROOT}` 가 자기 플러그인만 가리키는 문제와 부딪힌다 — `release-workflow`가
`project-conventions` 소유의 스크립트를 참조하려면 사본을 두어야 하고, 사본이 3벌(정본+2
소비처)이 되면 `validate-marketplace.sh` 에 교차 sha256 검사를 새로 추가해야 한다. 위임
패턴으로 바꾸면 이 문제 자체가 사라진다 — `notion_api.py` 는 `project-conventions` 안에만
있고, 다른 플러그인은 "존재하는가"만 확인한다.

### `check-agent-rules` 검사 7·8 이 "다른 플러그인과의 비교"가 아닌 이유

`release-workflow`·`product-planning` 은 `notion_api.py` 사본을 갖지 않는다. 검사 7·8 이
비교하는 것은 "프로젝트에 설치된 파일" ↔ "`project-conventions` 자신의 템플릿" 이며, 이는
기존 검사 5(`.mdc` ↔ `.md`)와 같은 성격이다 — 플러그인 내부의 생성물 검사이지 마켓플레이스
차원의 교차 검사가 아니다. 그래서 `scripts/validate-marketplace.sh` 에 새 검사를 추가하지
않았다.

### 검증

- `notion_mcp_gate.py` — 토큰 없음(무출력) / 토큰 있음(deny) / `NOTION_MCP_GATE=off`(무출력) /
  matcher 정규식(`^mcp__.*[Nn]otion`, 서버 접두사 3종 + 무관 서버) / 깨진 stdin(fail-open,
  exit 0) 5가지 케이스 확인
- `notion_api.py` — `--help`(서브커맨드 15개), `doctor --dry-run`(네트워크 무접촉),
  `.env` 파서(따옴표+인라인 주석 조합, 상위 폴더 fallback), `md2blocks`(PRD 템플릿 변환,
  `table` 블록 구조 확인). 이 과정에서 실제 버그 2건 발견·수정: `.env` 파서의 따옴표/주석
  처리 순서, `re.match()` 결과를 `bool` 로 감싸지 않아 JSON 직렬화가 실패하던 지점
- `install_agent_rules.py`/`check_agent_rules.py` — `--notion-rule off`(기본, `git-branch-workflow`
  만 설치) / `--notion-rule on`(4개 파일 + settings.json 훅 등록) / 재실행 멱등성(`PreToolUse`
  항목 1개 유지, 기존 `permissions`/`env` 키 보존) / `--notion-rule off` 재실행 시 기존
  설치물 미삭제 / 사본 훼손(tamper) → 검사 7 실패 → 원복 후 통과 / Notion 미설치 프로젝트에서
  검사 7·8·9 오탐 없음
- `bash scripts/validate-marketplace.sh` — 매 커밋 5개 검사 전부 통과 (검사 4a 오탐 1건을
  발견해 검사 자체를 수정)
- 버전 3곳(marketplace 엔트리·plugin.json·metadata.version) 수동 일치 확인 — 검사 2 는
  `name` 만 비교하고 `version` 은 비교하지 않으므로

### 버전

`project-conventions` 2.0.0 → **3.0.0** — 훅·스크립트 설치와 `.claude/settings.json` 편집이라는
새 산출물 카테고리가 생겼고, v1.4.0·v1.16.0 의 두 판단을 반전시킨다. `release-workflow` 1.1.0 →
**2.0.0**, `product-planning` 1.0.0 → **2.0.0** — 둘 다 Notion 을 필수에서 선택으로 낮추고 MCP
하드코딩을 전부 제거해, 기존에 MCP 로 동작하던 사용자에게는 동작 방식이 바뀐다. 나머지 3개
플러그인은 유지. 마켓플레이스 `metadata.version` 1.16.0 → **1.17.0**.

스킬 18개·플러그인 6개 유지 — 이번 릴리스는 새 플러그인도 새 스킬도 만들지 않는다. 기존 스킬
5개의 참조 방식을 바꾸고, `project-conventions` 의 기존 스킬 2개(`init-agent-rules`,
`check-agent-rules`)에 조건부 기능을 추가했을 뿐이다.

### 알려진 이슈

- **`db-create`·`view-create`·`page-create` 는 실계정 스모크 테스트를 거치지 않았다.**
  `POST /v1/databases`(`initial_data_source.properties` 중첩) · `POST /v1/views`
  (`configuration.group_by` 스키마) · table 블록(`table_row` children)의 요청 형태는 문서
  조사로 확정했으나, 실제 Notion 워크스페이스에 대고 실행해 검증하지는 않았다. 사용자가 처음
  `--notion-rule on` 을 켜고 `db-create`/`view-create` 를 실제로 부를 때 이 지점에서 형태
  불일치가 드러날 수 있다.
- **`main-branch-merge` 의 Notion 본문 수정 범위 축소는 코드로 강제되지 않는다.** `notion_api.py`
  에 본문 치환 서브커맨드가 없다는 사실 자체가 제약이지만, 스킬 문서는 "실패 시 리포트만"이라는
  기존 정책에 기댈 뿐 새 검증 스크립트를 추가하지 않았다.
- **`notion-api-only` 를 이미 설치한 프로젝트에 재실행 없이는 검사 7·8·9 가 새로 생기지 않는다.**
  이 릴리스 이전에 만들어진 사본은(존재할 수 없었지만, 향후 롤백 시나리오에서) 사용자가
  `init-agent-rules --notion-rule on` 을 다시 돌려야 검사 대상에 들어온다.
