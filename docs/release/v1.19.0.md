# v1.19.0

> 릴리스 날짜: 2026-09-06

`project-conventions:init-agent-rules` Step 1.5(Notion 연동 여부 질문)의 감지 범위를
넓힌다. 기존 세 신호("Notion 을 **쓰는가**"의 근거 — `.env` `NOTION_TOKEN`, `AGENTS.md`
언급, `@notionhq/client`)에 두 신호를 추가한다:

- `.claude/rules/notion-api-only.md` 가 이미 설치돼 있는지
- 그와 무관한 커스텀 Notion 규칙 파일이 `.claude/rules/` 아래에 이미 있는지

---

## 왜 필요했나

실사용 프로젝트 하나가 이 스킬의 `notion-api-only` 템플릿(MCP 차단 + 단일 REST 스크립트,
pull-only 기본)과는 다른, **되돌리기 난이도별 쓰기 정책**(속성 패치·신규 행은 즉시 진행,
본문 전체 교체 같은 되돌리기 어려운 쓰기는 dry-run→검증 필수)으로 진화한 자체 Notion
거버넌스를 이미 갖추고 있었다. `init-agent-rules` 를 다른 목적(자동 압축 임계값 설정)으로
재실행했을 때 Step 1.5 가 이 사실을 전혀 감지하지 못해, 만약 "예"를 그대로 골랐다면 서로
다른 두 워크플로가 동시에 설치돼 충돌할 뻔했다.

## 무엇이 달라지나

두 신호 중 앞의 것("이미 설치됨")은 기존 세 신호와 같은 방식으로 다룬다 — 근거로 제시하고
질문 문구만 "설치할지"에서 "재설치(갱신)할지"로 바꾼다.

뒤의 것("무관한 커스텀 Notion 규칙 존재")은 성격이 다르게 다룬다. 앞의 넷은 전부 "Notion 을
쓰는가"의 근거일 뿐이지만, 이건 "이미 다른 방식으로 관리 중"이라는 뜻이라 일반 템플릿을
그대로 설치하면 실제로 충돌한다. 그래서 다른 근거처럼 조용히 나열하지 않고
**"이미 `{파일명}` 이 있습니다 — 일반 템플릿을 설치하면 그 규칙과 겹칠 수 있는데 그래도
설치할까요?"** 로 따로 명시해 되묻는다.

이번에도 자동으로 "아니오" 처리하지 않는다 — 두 체계를 의도적으로 병행하려는 경우가 있을
수 있으므로, 지금까지와 같은 원칙대로 최종 판단은 사용자에게 남긴다.

## 변경 범위

감지는 스크립트가 아니라 스킬을 따르는 에이전트가 직접 수행하므로(`install_agent_rules.py`
에는 이 로직이 없다), 코드 변경이 없다.
