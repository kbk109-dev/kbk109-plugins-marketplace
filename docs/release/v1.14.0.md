# v1.14.0

> 릴리스 날짜: 2026-08-21

`main-branch-merge` 를 **버전명 없이 불러도 더 이상 중단하지 않는다.** 저장소 문맥에서 다음 버전
후보 3개를 계산해 추천과 함께 제시하고, 사용자가 고른 뒤에 릴리스를 진행한다. 지금까지는
"릴리스 버전명을 알려주세요" 를 출력하고 끝나서, 사용자가 태그를 찾아보고 다음 버전을 직접
계산해 타이핑해야 했다.

---

## ⚠️ 업데이트하면 달라지는 것

**버전 인자 없는 호출의 결말이 바뀐다.** 최신 태그와 프로젝트 매니페스트(`package.json`,
`app.json`, `app.config.*`)를 읽어 patch·minor·major 후보를 계산하고, `main..dev` 커밋 접두사로
어느 단계인지 판단해 번호 선택지를 띄운다.

**승인 없이는 한 발도 나가지 않는다.** 버전은 태그·커밋 메시지·`docs/release/` 파일명에 모두
박히고 push 뒤에는 되돌리기 어렵다. 부정 응답이면 파일·커밋·태그를 일절 만들지 않고 종료한다.

**버전을 인자로 준 호출의 동작은 그대로다.** 제안 단계 전체를 건너뛴다.

## ✨ Added

- **`compute_next_versions.py`** — 버전 목록에서 기준선과 후보 3개를 내는 결정적 스크립트.
  `main-branch-merge` 에 `scripts/` 가 생긴 것은 처음이다. 입력은 버전 배열 또는
  `{tags, manifests}` 객체를 받고, `baseline`·`candidates`·`mismatch`·`warnings` 를 JSON 으로 낸다.
- **Step 2.5 — 버전 제안 & 승인 게이트.** 문맥 수집 → 후보 계산 → 추천 판단 → 번호 제시 →
  승인 → 선택 후 검증의 6단계.

## 🔄 Changed

- **Step 2 의 태그 중복 확인이 조건부가 됐다.** 버전 제안은 `git tag` 조회가 전제이고 중복
  확인은 버전이 있어야 해서 서로 맞물린다. 체크 1~4 는 그대로 두고 체크 5만 Step 2.5 뒤로 미룬다.
- Step 1 에서 버전 미입력이 더 이상 치명적 오류가 아니다. `버전 미정` 으로 표시하고 진행한다.

## 🐛 Fixed

- **참조 파일 경로 2곳이 깨져 있었다.** `readme-best-practices.md` 와
  `release-note-best-practices.md` 를 `.claude/skills/…` 로 가리키고 있었는데, 플러그인 이관 전
  경로라 **설치한 사용자에게는 존재하지 않는 파일**이다. README 와 릴리스 노트를 그 가이드 없이
  쓰게 된다. `${CLAUDE_PLUGIN_ROOT}` 기준으로 고쳤다.

  `validate-marketplace.sh` 검사 4 는 `scripts/*.py|sh` 만 보고 `references/*.md` 는 안 봐서
  조용히 통과해 왔다. 검사 범위 확장은 이번에 하지 않았다.

## 기술 상세

### 왜 `compute_next_patch.py` 를 재사용하지 않았나

`fix-plan-impl` 에 이미 버전 계산 스크립트가 있지만 그것은 **patch 만** 올린다. major/minor 를
절대 건드리지 않는 것이 그 스킬의 존재 이유이므로(핫픽스 전용) 3후보 제시에는 쓸 수 없다.

대신 파싱 규칙은 두 스크립트가 같도록 맞췄다 — 선행 `v`/`V` 제거, pre-release 태그(`-rc1`)는
무시하고 `warnings` 기록, build metadata(`+build.5`)는 strip 후 비교. import 하지 않고 복제한
것은 스킬 간 파이썬 의존을 만들지 않기 위함이다.

### 기준선은 모든 소스의 최대값

태그와 매니페스트를 통틀어 가장 큰 값을 기준선으로 삼는다. 이미 공개된 버전보다 낮은 값을
제안하지 않기 위함이다. 두 소스가 어긋나면 `mismatch` 로 알리고 제안 화면에 그대로 띄운다 —
어느 파일이 뒤처졌는지가 정보이기 때문이다.

구현 중에 `mismatch` 불리언이 `mismatch_detail` 과 어긋나는 경우를 잡았다. 매니페스트 둘 중
하나만 태그와 다를 때 "최대값끼리 비교"로는 `false` 가 나오는데 detail 에는 경고가 들어 있어,
불리언만 보는 쪽이 경고를 건너뛴다. 판정을 detail 에서 파생시키도록 고쳤다.

### 산술은 스크립트, 판단은 모델

어느 단계를 추천할지는 `main..dev` 커밋 메시지로 모델이 정한다. `BREAKING CHANGE`·`!` 표기면
major, `feat:` 가 있으면 minor, 나머지면 patch.

**접두사를 판별할 수 없으면 추천을 붙이지 않는다.** 한글 커밋 등으로 근거가 없는데 추천을 달면
사용자는 그것을 근거가 있는 것으로 읽는다. 이때는 후보 3개만 제시하고 근거란에 "커밋 접두사
판별 불가"를 적는다. 추천은 힌트일 뿐이고 릴리스 단계 결정은 사용자의 판단이다 —
`release-plan` 의 SemVer 경고가 차단하지 않는 것과 같은 이유다.

### 검증

스크립트를 12케이스로 직접 호출해 확인했다 — 교차 확인/불일치 감지, 배열 입력, pre-release
무시, build metadata strip, 매니페스트가 태그보다 큰 경우, 태그 없이 매니페스트만, 매니페스트
끼리 불일치, `version` 필드 누락, 종료코드 2(초기 릴리스)·3(입력 오류), 그리고
`compute_next_patch.py` 와 patch 값이 일치하는지.

이 저장소에서 Step 2.5 의 ①②를 실제로 돌려 기준선 `v1.13.0`, 후보 `1.13.1 / 1.14.0 / 2.0.0` 을
확인했다. `validate-marketplace.sh` 5개 검사 전부 통과 — 신규 스크립트 참조 dangling 0건 포함.

### 버전

`release-workflow` 1.0.0 → **1.1.0**. 나머지 5개 플러그인은 유지. 마켓플레이스
`metadata.version` 1.13.0 → **1.14.0**. 기존 동작을 깨지 않고 진입 경로를 하나 더한 것이므로
MINOR 다.

스킬 18개 · 플러그인 6개 유지. `main-branch-merge/SKILL.md` 는 295 → 390줄로 AGENTS.md 의
500줄 목표 안이다. 이 저장소는 `package.json` / `app.json` 이 없는 플러그인 마켓플레이스라
Expo 빌드 번호는 해당 없음.

### 알려진 이슈

- **새 게이트로 자기 자신의 릴리스를 진행할 수는 없었다.** 마켓플레이스 소스가 GitHub 이고
  설치본은 캐시된 1.0.0 이라, 이 변경이 `main` 에 올라가기 전에는 새 Step 2.5 가 로드되지 않는다.
  이번 릴리스는 작업 트리의 SKILL.md 를 따라 수동으로 진행했다. **다음 릴리스부터 실제 경로를
  탄다** — `/plugin marketplace update` 후 버전 없이 호출하면 된다.
- **미리 올린 매니페스트가 기준선을 오염시킬 수 있다.** 이 저장소는 AGENTS.md 규칙상 작업
  커밋에서 매니페스트 버전을 먼저 올리므로, `marketplace.json` 을 매니페스트 소스에 넣었다면
  기준선이 아직 배포 안 된 `1.14.0` 으로 잡혀 후보가 `1.14.1 / 1.15.0` 이 됐을 것이다. 현재
  스킬이 보는 매니페스트 목록(`package.json`·`app.json`·`app.config.*`)에는 없어서 문제가 되지
  않았지만, 같은 관례를 쓰는 프로젝트에서는 태그를 기준선으로 쓰는 편이 안전하다.
- **커밋 접두사 판별은 Conventional Commits 를 전제한다.** 이 저장소는 그 관례를 쓰지만, 한글
  커밋만 있는 프로젝트에서는 추천 없이 후보 3개만 뜬다. 의도된 동작이다.
- **evals 가 없다.** `main-branch-merge` 는 `release-workflow` 4개 스킬 중 유일하게
  `evals/evals.json` 이 없고 이번에도 추가하지 않았다.
- Notion Tasks DB 매핑 불가 — 이 저장소는 Notion 을 상태 저장소로 쓰지 않는다.
