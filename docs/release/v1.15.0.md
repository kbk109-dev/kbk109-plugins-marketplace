# v1.15.0

> 릴리스 날짜: 2026-08-21

`harness-dev` 의 **"8가지 기계적 제약"이 실제로는 전부 산문이었다.** 플러그인에 실행 파일이 하나도
없었고, 제약은 SKILL.md 에 적힌 지시일 뿐이었다. 다섯을 실행 시점에 검사하는 코드로 옮기고,
코드가 볼 수 없는 셋은 컨텍스트 압축을 견디는 자리로 옮긴다.

---

## ⚠️ 업데이트하면 달라지는 것

**이 플러그인에 훅이 생긴다.** `PreToolUse` 로 `Write|Edit` 를 받아
`docs/harness/*/feature_list.json` 쓰기만 판정한다. 켜진 모든 프로젝트에서 발화하지만 **첫 분기가
`file_path` 문자열 검사뿐**이라 무관한 호출은 파일을 열기도 전에 빠진다. 대신 호출당 파이썬 기동
비용(수십 ms)이 상시로 붙는다 — `project-conventions` 가 Bash 매처에 대해 감수한 것과 같은
종류의 비용이다.

**`feature_list.json` 에 `attempts` 필드가 생긴다.** 제약 7(재시도 상한 2회)의 카운터가 지금까지
세션 컨텍스트에만 있어서 세션이 끊기면 사라졌다. 필드가 없으면 0으로 보므로 기존 실행은 그대로
동작한다.

**Phase 1 승인 직후 대상 프로젝트의 `AGENTS.md` 에 규율 블록이 설치된다** (없으면 `CLAUDE.md`,
둘 다 없으면 `AGENTS.md` 신규 생성). 되돌리려면 `harness_agents_block.py --remove`.

## 기술 상세

### 규율과 진행 상태를 섞지 않는다

설계 검토에서 걸러낸 실패안이 하나 있다 — slug 별 "**Harness 진행 중**" 블록을 AGENTS.md 에
설치하고 종료 시 제거하는 방식이었다.

이건 **어느 실행이 활성인지**라는 진행 상태의 두 번째 사본을 AGENTS.md 에 만든다.
`docs/harness/*/feature_list.json` 만 보면 아는 사실이고, 중단된 실행에서 블록이 남으면
AGENTS.md 가 **틀린 지시**를 하게 된다 — `refresh-agent-rules` 가 존재하는 이유가 정확히
"틀린 지시는 없는 지시보다 나쁘다"이다. AGENTS.md 의 다른 어떤 내용도 수명주기를 갖지 않는데
여기만 예외가 되는 것도 문제였다.

그래서 역할을 갈랐다. **규율**(8가지 제약, 실행마다 동일)은 AGENTS.md 에, **진행 상태**(어디까지
갔나)는 `progress.md` · `feature_list.json` 에 둔다. 설치되는 블록에는 slug 도 "진행 중" 도 없고,
상태 위치를 가리키는 포인터만 있다 — 포인터는 글로브라 항상 참이고 상하지 않는다. 그래서 작업이
끝나도 제거하지 않는다. `progress.md` 의 역할은 그대로이고, 오히려 블록이 그쪽을 가리킨다.

### 훅이 할 수 있는 것과 없는 것

플러그인 훅이 전역 발화해도 안전하려면 **차단이 복구 가능해야 한다** — 같은 호출을 그대로 다시
하면 반드시 통과해야, 훅이 오판했을 때 최대 대가가 도구 호출 한 번 재시도로 유계다. 이 훅도 같은
`(에이전트, 위반)` 을 한 번만 차단한다.

**그래서 훅은 제약을 불가능하게 만들지 못한다.** 만드는 것은 조용한 지름길을 **의도적인 선택으로**
바꾸는 것이다 — 재호출하려면 모델이 위반을 읽고 다시 결정해야 하고, 그 사실이 상태 파일에 남는다.
불가능하게 만드는 쪽은 스프린트마다 도는 검증 스크립트이고, 사람이 그 결과를 본다.

키를 파일 내용이 아니라 **위반의 종류**로 잡는다. 내용 해시로 잡으면 무관한 한 글자만 바꿔도 새
키가 되어 매번 차단되고, 그게 곧 루프다.

### 잠금 파일의 타이밍

제약 2 는 `docs/harness/{slug}/.criteria_lock.json` 에 acceptance_criteria 지문을 남겨 비교한다.
잠금은 **Phase 1 사용자 승인 직후에만** 쓴다 — 승인 전에 잠그면 사용자의 계획 수정이 그대로
위반으로 잡히고, 스프린트 도중에 쓰면 제약 2 가 무의미해진다. `--update-lock` 이 잠금을 새로
쓰는 유일한 경로인 이유다.

순서만 바꾼 것은 위반이 아니고(내용이 같다), 문구를 고치거나 항목을 지우면 잡힌다. 잠금 파일
자체도 모델이 고칠 수 있으므로 **위조 불가능하게 만드는 장치가 아니라, 고치면 눈에 띄게 만드는
장치다.**

### 규칙 모듈을 훅과 스크립트가 공유한다

`hooks/_feature_list_rules.py` 하나를 양쪽이 import 한다. 규칙을 복제하면 훅의 판정과 사람이
돌리는 검사가 갈라진다 — 통과했다고 믿었는데 막히거나, 막혔어야 할 것이 통과한다. **이 플러그인이
막으려는 실패와 같은 종류다.** 훅 쪽 런타임 계약이 더 엄격해서(예외 삼킴·무출력) 원본을 그쪽에
두고, 스킬 스크립트가 한 단계 위 경로를 `sys.path` 에 넣어 가져온다.

### 알려진 이슈

- **훅이 실제 플러그인 로딩 경로를 아직 타지 않았다.** 스모크 테스트는 스크립트를 직접 호출한
  것이라 `${CLAUDE_PLUGIN_ROOT}` 치환과 `hooks.json` 등록은 검증되지 않았다. **업데이트 후 첫
  확인 사항은 무관한 파일 편집이 아무 일 없이 지나가는지**다. 이상하면
  `/plugin uninstall harness-devkit` 로 즉시 끌 수 있다.
- **`/plugin marketplace update` 는 실행 중인 세션에 반영되지 않는다.** 디스크만 갱신되고
  세션은 시작 시점의 레지스트리를 계속 쓴다. `/reload-plugins` 또는 세션 재시작이 필요하다.
  이번 릴리스도 그 때문에 v1.14.0 에서 만든 버전 제안 게이트를 쓰지 못하고 수동으로 진행했다.
- **판단 영역 셋(제약 1·3·5)은 여전히 강제되지 않는다.** AGENTS.md 규율 블록이 컨텍스트 압축을
  견디게 할 뿐이다. `sprint_reports/` 의 채점 근거를 사람이 들여다보는 일은 계속 필요하다.
- **`harness-dev` 에 evals 가 없다.** `release-workflow` 4개 스킬과 달리 `evals/evals.json` 이
  이번에도 추가되지 않았다.
- Notion Tasks DB 매핑 불가 — 이 저장소는 Notion 을 상태 저장소로 쓰지 않는다.
