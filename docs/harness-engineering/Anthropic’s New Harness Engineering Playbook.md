# **Why AI Agents Keep Failing: Problem With Long-Running Agents**

AI 에이전트를 사용하는 대부분의 개발자는 동일한 문제를 겪습니다.

에이전트는 간단한 리팩토링, 단일 기능 구현, 특정 버그 수정과 같은 짧은 작업에는 잘 작동합니다.

> ***하지만 여러 세션에 걸쳐 진행되는 복잡한 작업을 맡기는 순간, 예측하기 어렵고 디버깅하기도 힘든 방식으로 품질이 저하되기 시작합니다.***
> 

Anthropic은 이 문제를 광범위하게 문서화했으며, 실패 패턴은 더욱 구체적입니다.

### **Four Ways Agents Go Off the Rails**

![Harness Engineering](https://miro.medium.com/v2/resize:fit:661/1*Usp3x60Yp9AT6OBUvhzWsg.png)

1. **모든 것을 한 번에 처리하려 함(They try to do everything at once)**

에이전트에게 "풀스택 웹 앱을 만들어 줘"와 같은 포괄적인 지시를 내리면, 에이전트는 한 번에 모든 것을 처리하려고 시도합니다.

> ***계획 없이 기능 구현을 시작하고, 컨텍스트 창을 절반쯤 소모한 후, 다음 세션에서는 문서화도 없이 미완성된 코드베이스를 이어받아 작업을 진행합니다.***
> 

다음 에이전트 세션은 아무런 정보 없이 시작하여 대부분의 시간을 무슨 일이 일어났는지 추측하는 데 소비하고, 이 과정이 반복됩니다.

1. **컨텍스트 불안(Context anxiety)**

에이전트의 컨텍스트 창이 가득 차면, 일부 모델은 한계에 다다랐다고 감지하고 작업을 조기에 종료하기 시작합니다.

> ***Anthropic은 Claude Sonnet 4.5에서 이러한 현상을 관찰했습니다.*** 모델은 속도가 느려지고, 구축 대신 요약을 시작하며, 완료되지 않은 작업에 대해 완료 신호를 보냅니다.
> 

연구진은 이를 "맥락 불안"이라고 명명했는데, 에이전트가 이러한 행동을 할 때는 자신감 있는 것처럼 보이기 때문에 포착하기 어려운 오류 유형 중 하나입니다.

1. **너무 일찍 성공을 선언함(Declaring victory too early)**

에이전트는 기본적으로 낙관적입니다.

몇 세션 동안 진행 상황을 확인한 후, 다음 에이전트 인스턴스는 주변을 둘러보고 의미 있는 작업이 완료되었다고 판단하여 일부 기능이 아직 구축되지 않았더라도 프로젝트가 완료되었다고 결론짓습니다.

완료된 작업과 완료되지 않은 작업에 대한 체계적인 기록이 없으면 에이전트는 실제 작업 범위에 고정되지 않습니다.

1. **자기 평가 편향(Self-evaluation bias)**

에이전트에게 자신의 출력물을 검토하도록 요청하면 거의 항상 좋다고 답합니다.

이는 연구에서 발견된 불편한 결과 중 하나입니다. Anthropic은 UI 디자인과 같은 주관적인 작업과 기능 소프트웨어 개발과 같은 객관적인 작업 모두에서 이를 테스트했습니다.

> ***두 경우 모두 에이전트는 자신의 작업을 평가했으며, 인간 검토자가 즉시 평범하거나 결함이 있다고 지적할 결과물을 승인하는 경우가 많았습니다.***
> 

사물을 만든 에이전트는 자신이 만든 사물을 신뢰할 수 있게 평가할 수 없습니다.

### **Why a Better Model Doesn’t Fix This**

에이전트가 실패할 때 가장 확실한 해결책은 모델을 업그레이드하는 것입니다.

하지만,

> ***더 나은 성능을 가진 모델이라도 제대로 설계되지 않은 환경에서는 결국 같은 방식으로 실패할 것입니다.***
> 

이것이 바로 Anthropic의 하네스 엔지니어링 연구의 핵심적인 통찰입니다.

# **Two-Part Solution**

2025년 11월에 발표된 이 논문은 Anthropic이 처음으로 실제로 구현한 솔루션을 문서화한 자료입니다.

> ***모델을 완전히 개편하는 대신, 초기화 에이전트와 코딩 에이전트라는 두 부분으로 구성된 간단한 구조를 구축했습니다. 각 에이전트는 명확한 역할과 경계를 가지고 있습니다.***
> 

### **Initializer Agent**

첫 번째 세션은 이후의 모든 세션과 완전히 다릅니다.

> ***첫 번째 세션의 역할은 환경을 설정하고, 이후 모든 세션의 기반이 되는 토대를 마련하는 것입니다.***
> 

첫 번째 세션은 다음 세 가지를 생성합니다.

- ***feature_list.json** — 사용자의 프롬프트를 개별 기능으로 확장한 구조화된 JSON 파일이며, 각 기능은 기본적으로 실패로 표시됩니다. Anthropic의 [claude.ai](http://claude.ai/) 클론 테스트에서는 각 기능에 대한 구체적인 통과/실패 단계를 포함하는 200개 이상의 세분화된 기능이 생성되었습니다.*
- ***claude-progress.txt** - 각 세션이 작업을 마칠 때 기록하는 진행 로그 파일로, 다음 에이전트가 추측 없이 현재 진행 상황을 파악할 수 있도록 합니다.*
- [***init.sh](http://init.sh/) + 초기 Git 커밋** - 개발 서버를 시작하고 새로운 작업이 시작되기 전에 기준 엔드투엔드 테스트를 실행하는 셸 스크립트입니다.*

> ***Anthropic은 모델이 JSON을 실수로 덮어쓰거나 형식을 변경할 가능성이 적기 때문에 기능 목록에 Markdown 대신 JSON을 사용했습니다.***
> 

또한 에이전트가 구현할 수 없는 기능을 삭제하지 못하도록 "테스트를 제거하거나 편집하는 것은 허용되지 않습니다"와 같은 명시적인 지침을 사용했습니다.

![Harness Engineering](https://miro.medium.com/v2/resize:fit:671/1*iVodYFis_19q0K5P5pB2eQ.png)

### **Coding Agent**

첫 번째 세션 이후의 모든 세션은 코드를 한 줄 작성하기 전에 다음과 같은 오리엔테이션 순서를 따릅니다.

1. `*pwd` 실행 - 현재 작업 디렉토리 확인*
2. `*claude-progress.txt` 및 git log 확인 - 마지막 작업 내용 파악*
3. `*feature_list.json` 확인 - 우선순위가 가장 높은 미완성 기능 선택*
4. `*init.sh` 실행 - 개발 서버 시작*
5. *기준선 엔드투엔드 테스트 실행 - 새로운 작업을 추가하기 전에 기존 버그 발견*
6. *한 번에 하나의 기능 작업*

> ***마지막 규칙, 즉 한 번에 하나의 기능만 작업하는 것이 이 시스템에서 가장 중요한 규칙으로 밝혀졌습니다. 이 기능이 없으면 에이전트는 여러 기능을 동시에 시도하다가 세션 도중에 진행 상황을 놓치게 됩니다.***
> 

매 세션이 끝날 때마다 코딩 에이전트는 다음을 수행해야 합니다.

- *모든 변경 사항을 설명 메시지와 함께 Git에 커밋*
- *수행된 작업에 대한 명확한 요약을 포함하여 진행 상황 파일 업데이트*
- *코드를 작성한 후가 아니라 적절한 엔드투엔드 테스트를 완료한 후에만 기능 통과 표시*

명시적인 프롬프트가 없으면 에이전트는 사용자 관점에서 기능이 제대로 작동하는지 확인하지 않고 코드를 작성한 후 기능을 완료로 표시할 수 있습니다.

> ***Anthropic이 에이전트에게 Puppeteer MCP에 대한 접근 권한을 부여하고 사람처럼 테스트하도록 요구하자 기능 정확도가 크게 향상되었습니다.***
> 

이 구조는 효율적인 소프트웨어 엔지니어의 작업 방식과 유사합니다.

> ***스프린트 중간에 프로젝트에 합류한 개발자는 저장소의 모든 파일을 읽지 않습니다. 최근 커밋을 확인하고, 작업 보드를 읽고, 앱을 실행한 다음 다음 티켓을 선택합니다.***
> 

Anthropic은 이러한 워크플로를 에이전트 프롬프트에 반영했습니다.

- 초기화 프로그램이 인프라를 구축합니다.
- 코딩 에이전트가 프로세스를 따라갑니다.
- Git 히스토리와 진행률 파일이 세션 간의 인수인계를 처리합니다.

이러한 접근 방식 덕분에 여러 컨텍스트 창에서 안정적으로 작동합니다.

# **Generator-Evaluator Loop and Three-Agent Architecture**

초기화 및 코딩 에이전트 구조는 어느 정도까지는 작동했지만, 한계가 있었습니다.

더 복잡한 빌드에서는 다음과 같은 문제가 발생했습니다.

- *기능이 완전히 구현되지 않고 스텁 처리됨*
- *UI는 완성된 것처럼 보이지만 사용 즉시 오류가 발생함*
- *에이전트가 자신의 작업을 평가하도록 요청받았을 때, 사람이 검토하면 즉시 거부할 내용을 승인함*

> ***Anthropic의 2026년 3월 논문에서는 이러한 한계를 극복한 방법을 설명합니다. 그들이 선택한 접근 방식은 생성적 적대 신경망(GAN) 아키텍처에서 영감을 얻었습니다. GAN에서는 두 모델이 경쟁하는데, 하나는 출력을 생성하고 다른 하나는 이를 거부하려고 합니다.***
> 

에이전트 설계에 적용하면 이 아이디어는 간단합니다. **작업을 수행하는 에이전트와 작업을 평가하는 에이전트를 분리하는 것입니다.**

### **Self-Evaluation Problem**

에이전트에게 자신의 결과물을 검토하도록 요청하면 거의 항상 승인합니다.

> ***Anthropic은 UI 디자인과 같은 주관적인 작업과 기능 소프트웨어 개발과 같은 객관적인 작업 모두에서 이를 테스트했습니다. 두 경우 모두 에이전트는 스스로에게 관대하게 점수를 매겼습니다. 사소한 문제는 지적하면서도 실제 사용자에게 영향을 미치는 문제가 있는 작업은 승인했습니다.***
> 

결과물을 생성한 것과 동일한 논리가 평가를 수행합니다. 즉, 자신의 결정에 편향될 수밖에 없습니다.

> ***평가자가 여전히 LLM(Learning Leadership Model)이고 LLM은 LLM이 생성한 결과물에 관대하기 때문에 생성자와 평가자를 분리해도 이 문제는 해결되지 않습니다.***
> 

하지만 독립형 평가자를 회의적으로 조정하는 것이 생성자가 자신의 결과물을 비판적으로 평가하도록 만드는 것보다 훨씬 더 실현 가능합니다. 외부 피드백이 존재하게 되면 생성자는 개선해야 할 구체적인 기준을 갖게 됩니다.

### **Three-Agent System**

![](https://miro.medium.com/v2/resize:fit:662/1*9Am6HrbRIMbHWurFubHiGQ.png)

업데이트된 아키텍처는 generator-evaluator loop에 planner를 추가하여 3개의 에이전트로 구성된 시스템을 만듭니다.

**Planner**

- ***1~4문장으로 된 프롬프트를 바탕으로 완전한 제품 사양을 작성합니다.***
- ***세부적인 구현보다는 제품 범위와 전반적인 방향에 집중합니다.***
- ***코드를 작성하기 전에 시각적 언어를 정의하기 위해 Anthropic’s frontend design skill을 활용합니다.***
- ***상위 단계의 오류가 생성기가 구축하는 모든 것에 영향을 미치므로 구현 세부 사항을 과도하게 명시하지 않습니다.***

**Generator**

- ***플래너의 사양을 기반으로 스프린트별로 애플리케이션을 구축합니다.***
- ***각 스프린트 시작 전에 평가자와 스프린트 계약을 협의하여 코드를 작성하기 전에 "완료"의 기준을 정합니다.***
- ***각 스프린트 종료 후 인계하기 전에 자체 평가를 수행합니다.***

**Evaluator**

- ***Playwright MCP를 사용하여 실제 사용자처럼 앱을 탐색합니다.***

# **Final Thoughts**

하네스는 단순한 프롬프트나 시스템 메시지가 아니라, 모델을 중심으로 구축하는 전체 환경을 의미합니다.

> ***여기에는 제약 조건, 도구, 피드백 루프, 인수인계 산출물, 그리고 에이전트의 성공 또는 실패 여부를 결정하는 구조 등이 포함될 수 있습니다.***
> 

차이점은 다음 다섯 가지에 있습니다.

- ***작업 분해** - 에이전트에게 무한한 목표를 제시하는 대신, 작업을 개별적이고 검증 가능한 단위로 나누는 것*
- ***세션 연속성** - 진행 파일이나 Git 기록과 같은 구조화된 산출물을 통해 각 세션이 이전 세션이 끝난 지점부터 이어지도록 하는 것*
- ***외부 평가** - 빌더가 직접 작업을 평가하는 대신, 별도의 에이전트 또는 프로세스를 통해 결과물을 평가하는 것*
- ***기계적 제약 조건** - 모델이 재정의할 수 없는 경계를 설정하는 규칙*
- ***점진적 검증** - 실제 사용자가 작업을 완료하고 다음 단계로 넘어가기 전에 각 작업 단위를 테스트하는 것*
