# Git 브랜치 워크플로

이 저장소에서 일상 작업 요청을 받을 때 따르는 브랜치·커밋·머지 절차다.

에이전트가 다루는 최상단 브랜치는 `dev` 다. 릴리스 브랜치 `{{MAIN_BRANCH}}` 에는 사람이 직접
머지하므로, 에이전트에게는 작업의 기점도 머지 대상도 아니다.

## 1. 작업 시작 — dev 에서 분기

작업 요청을 받으면 먼저 현재 브랜치를 확인한다 (`git branch --show-current`).

| 현재 위치 | 처리 |
|---|---|
| `{{MAIN_BRANCH}}` | `dev` 로 이동한 뒤, `dev` 에서 새 작업 브랜치를 만들어 작업한다 |
| `dev` | `dev` 에서 새 작업 브랜치를 만들어 작업한다 |
| 그 외 브랜치 | 3절의 판단을 거친다 |

- **`dev` 가 없으면 만든다** — `git switch -c dev {{MAIN_BRANCH}}`. 묻지 않고 만들어도 된다.
  dev 의 존재는 이 규칙의 전제이지 사용자에게 확인받을 선택지가 아니다.
- 사용자가 "`{{MAIN_BRANCH}}`에서 해" 또는 "이 브랜치에서 계속해" 라고 명시한 경우만 예외.

## 2. 브랜치 이름

형식: `{영문접두사}/{한글-간단-설명}`

| 접두사 | 용도 |
|--------|------|
| `feat/` | 기능·규칙·문서 추가 |
| `fix/` | 버그·깨진 동작 수정 |
| `docs/` | 문서만 |
| `chore/` | 설정·검증·잡무 |
| `refactor/` | 동작 동일 리팩터 |
| `test/` | 테스트·eval |

- 설명은 짧게, 공백 대신 `-`.
- 예: `feat/브랜치-워크플로-규칙`, `fix/로그인-리다이렉트-오류`

## 3. 이미 다른 브랜치에 있을 때

`{{MAIN_BRANCH}}` 도 `dev` 도 아닌 브랜치에 있으면 먼저 그 브랜치가 무슨 작업 중인지 확인한다.

```bash
git status --short
git log --oneline dev..HEAD
```

그리고 **스스로 판단해** 둘 중 하나를 고른다. 매번 사용자에게 되묻지 않는다 — 판단 기준이
아래에 있으므로 묻는 것은 결정을 떠넘기는 것일 뿐이다.

| 선택 | 조건 |
|---|---|
| **이어서 계속** | 새 요청이 그 브랜치가 하던 일의 연장·수정·후속이다 |
| **`dev` 로 머지하고 새 브랜치** | 새 요청이 그 브랜치와 다른 주제다 |

"`dev` 로 머지하고 새 브랜치" 를 택했으면 순서는 이렇다.

1. 미커밋 변경이 있으면 4절 커밋 게이트를 먼저 거친다
2. `git switch dev` → `git merge --no-ff <이전-브랜치>`
3. `git branch -d <이전-브랜치>`
4. `dev` 에서 새 작업 브랜치를 만든다

**어느 쪽을 택했는지와 그 근거를 한 줄로 밝히고 진행한다.** 사용자가 판단을 뒤집으려면
무엇이 결정됐는지 알아야 한다.

미커밋 변경이 남아 있는데 사용자가 커밋을 승인하지 않으면 **"이어서 계속"을 택한다.**
승인받지 못한 변경을 들고 브랜치를 옮기지 않는다 — 브랜치 정리가 커밋 게이트를 우회하는
뒷문이 되면 안 된다.

## 4. 커밋 게이트

- 작업이 끝나도 **절대 자동 커밋하지 않는다.**
- 변경 요약을 보여 주고 **커밋 여부를 확인**한다.
- 사용자가 승인한 뒤에만 커밋한다.
- 커밋 메시지: 영문 접두어 + 한글 설명.
- 커밋 전 반드시: `{{PRE_COMMIT_CHECK}}`

## 5. 머지 — dev 까지만

- 작업 브랜치는 **`dev` 로만** 머지한다. 커밋 승인·완료 후에만 진행한다.
- `git switch dev` → `git merge --no-ff <작업-브랜치>` → `git branch -d <작업-브랜치>`
- **어떤 경우에도 `{{MAIN_BRANCH}}` 에 머지하지 않는다.** `{{MAIN_BRANCH}}` 브랜치를 체크아웃해
  머지·리베이스·푸시·태그를 수행하지 않는다. `dev` → `{{MAIN_BRANCH}}` 머지는 **사람이 직접** 한다.
- **push 는 별도 승인 전까지 하지 않는다.**
- PR 생성은 사용자가 요청한 경우에만. 대상 브랜치는 `dev` 다.

## 6. 스킬 예외

- 스킬이 브랜치·커밋 절차를 따로 규정하면 **그 스킬이 우선**한다. 이 규칙은 일상 작업 요청용이다.
- 5절의 `{{MAIN_BRANCH}}` 머지 금지에는 예외가 하나뿐이다 — **사용자가 릴리스 스킬을 직접
  호출한 경우.** 사람이 그 시점을 고른 것이므로 "사람이 직접"에 해당한다.
  에이전트가 스스로 릴리스 스킬을 불러 `{{MAIN_BRANCH}}` 에 머지하는 것은 금지다.
