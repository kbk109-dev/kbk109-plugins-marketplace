# 단계마다 새 서브에이전트, 진입 스킬은 얇은 오케스트레이터

1.x 의 `harness-dev` 는 한 세션 안에서 Planner·Generator·Evaluator 역할을 전환했다. 같은 컨텍스트가
방금 쓴 코드를 평가하니 자기평가 편향이 그대로였고, 세션이 끊기면 대화 안의 계약·판단이 사라졌다.
2.0 은 PRD·PLAN·TC·구현·QA 를 단계마다 새 서브에이전트가 맡고, 메인 세션(진입 스킬)은 사용자 대화와
호출 순서 지휘와 상태 파일 갱신만 한다. 연속성은 전부 `docs/harness/<slug>/` 의 파일이 맡고,
"지금 어느 단계인가" 는 모델이 아니라 `harness_state.py` 가 파일 상태에서 판정한다.

## Considered Options

- **단계별 스킬 5~6개**: 사용자가 단계를 직접 부를 수 있지만 description 이 상시 비용으로 늘고 스킬 간
  안티트리거가 필요하다. 진입 스킬 하나 + 플러그인 루트 에이전트로 가고, 호출은 상태가 정한다.
- **한 세션 역할 전환 유지**: 가장 가볍지만 자기평가 편향이 남는다. 문서 단계의 critic 과 QA 의
  evaluator 는 구현·작성 과정을 모르는 별개 컨텍스트여야 판정이 독립이다.

## Consequences

- 서브에이전트는 사용자와 대화할 수 없고 다른 서브에이전트를 부를 수 없다 → 인터뷰·승인은 메인,
  generator→evaluator 릴레이도 메인이 지휘한다.
- 에이전트 description 은 Agent 도구 목록에 상시 로드된다 → 짧게 쓴다.
- `pass` 를 evaluator 만 기록하는 규칙은 훅이 한 번 막고 검증 스크립트가 최종으로 잡는다.
  훅은 전역 발화하므로 복구 가능해야 한다 (같은 호출을 다시 하면 통과).
- 되돌리기 어렵다: 상태 파일 레이아웃과 에이전트 계약이 1.x 와 다르다. 1.x 레이아웃은 `legacy`
  stage 로만 재개를 지원한다.
