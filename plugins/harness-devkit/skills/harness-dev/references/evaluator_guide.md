# Evaluator 상세 가이드

`agents/evaluator.md` 가 정본이다. 이 문서는 판정 원칙과 증거의 기준을 설명한다.
evaluator 는 **회의적 심사관**이다 — 겉보기에 작동하는 것과 실제로 작동하는 것을 구분하고,
증거 로그가 없는 PASS 는 존재하지 않는다.

## 왜 별개 서브에이전트인가

generator 와 같은 컨텍스트에서 역할만 바꾸면 방금 쓴 코드에 대한 호감이 판정에 섞인다
(자기평가 편향). 별개 서브에이전트는 구현 과정을 모르고 **TC 와 증거만** 본다. 튜닝도 쉽다 —
"회의적이어라" 는 지시는 구현자보다 심사자에게 걸 때 잘 지켜진다.

## 판정의 근거 = 확정 TC

판정 기준은 evaluator 의 취향이 아니라 `.tc_lock.json` 으로 잠긴 TC 다. 시작 전에 `tc-check` 로 TC 가
바뀌지 않았는지 확인한다. 이 때문에 evaluator 는 TC 를 고치지 않는다 — 고치면 기준을 완화하는
지름길이 된다. TC 가 부당하다고 판단되면 FAIL 이 아니라 사유와 함께 `blocked` 로 보고한다.
레거시 레이아웃(TC.md 없음)은 `acceptance_criteria` 가 판정 기준이다.

## 실행 순서

1. 기계 검사 — `validate_feature_list.py --stubs <구현 경로>`. 위반이 있으면 TC 를 돌릴 것도 없이 FAIL
   (제약 2·4·6·7·8·10·11 은 점수 대상이 아니라 통과/실패다)
2. 해당 FID 의 TC **전부** 실행. 하나라도 FAIL 이면 기능은 FAIL
3. 영향 범위의 기존 기능 TC 회귀
4. 보고서·status 기록, 그리고 갱신 전 사본과 `--prev` 비교

## 증거의 기준

- 로그는 `logs/<FID>/<n>.log`, TC 마다 하나. 명령 · 종료 코드 · 출력을 **실제 그대로** 담는다
  (길면 끝 100줄). 요약해서 쓰거나 기대 결과를 적어 넣지 않는다.
- 앱 기동이 필요한 TC 는 PLAN 의 `start` 로 띄운다. 띄우지 못하면 PASS 가 아니라 FAIL 이다.
- 실행할 수 없는 TC(도구 없음, 환경 제약)는 PASS 로 두지 않는다. 사유와 함께 FAIL 로 보고해
  사용자가 환경을 고치거나 TC 를 재검토하게 한다.
- 시각 결과는 Playwright MCP 가 있으면 그것으로, 없으면 PLAN 의 `e2e` 명령의 출력으로 판정한다.

## 평가 원칙

- 관대한 점수 금지. 의심스러우면 FAIL 이고, 그 의심을 재현하는 TC 를 피드백에 쓴다.
- 사용자 경험에 영향을 주는 문제는 반드시 지적한다. 사소한 문제는 non-blocking 으로 적고 넘어간다.
- PreCompletion Checklist — PASS 전에 모두 확인: ① 해당 FID 의 모든 TC 통과 ② 기존 기능 회귀 없음
  ③ 엔드투엔드 흐름 한 번 완주 ④ 기계 검사 통과

## FAIL 피드백

generator 가 그대로 따라 할 수 있어야 한다: 문제 위치(파일:줄), 원인, 수정 방향, 재현 TC id.
"더 개선하세요" 같은 막연한 피드백은 재작업을 낭비시킨다.

## 상태 기록

| 결과 | status | attempts |
|---|---|---|
| PASS | `pass` + `evidence` + `eval_report` | 그대로 |
| FAIL (attempts < 2) | `fail` | +1 |
| FAIL (attempts = 2, 3번째) | `blocked` | 2 유지 (상한 초과는 제약 7 위반) |

`pass` 는 되돌릴 수 없다 (제약 10). 이미 pass 인 기능이 회귀로 깨지면 status 를 되돌리지 않고
보고서에 적어 사용자에게 올린다.

## 에픽 회귀 모드 (`mode: epic`)

에픽 종료 직전 `/simplify` 가 코드를 고친 뒤 호출된다. 확정 TC 전체를 다시 실행하고 `eval/EPIC.md` 만
쓴다 (`VERDICT: PASS|FAIL`). 개별 기능의 status 는 건드리지 않는다.
