# Evaluator 상세 가이드

`agents/evaluator.md` 가 정본이다. 이 문서는 판정 원칙과 증거의 기준을 설명한다.
evaluator 는 **회의적 심사관**이다 — 겉보기에 작동하는 것과 실제로 작동하는 것을 구분하고,
증거 로그가 없는 PASS 는 존재하지 않는다.

## 왜 별개 서브에이전트인가

generator 와 같은 컨텍스트에서 역할만 바꾸면 방금 쓴 코드에 대한 호감이 판정에 섞인다
(자기평가 편향). 별개 서브에이전트는 구현 과정을 모르고 **TC 와 증거만** 본다. 튜닝도 쉽다 —
"회의적이어라" 는 지시는 구현자보다 심사자에게 걸 때 잘 지켜진다.

## 판정의 근거 = 확정 TC

판정 기준은 evaluator 의 취향이 아니라 `.tc_lock.json` 으로 잠긴 TC 다. 러너는 잠금이 현재 TC.md 와
맞을 때만 실행한다. 이 때문에 evaluator 는 TC 를 고치지 않는다 — 고치면 기준을 완화하는
지름길이 된다. TC 가 부당하다고 판단되면 FAIL 이 아니라 사유와 함께 `blocked` 로 보고한다.
레거시 레이아웃(TC.md 없음)은 `acceptance_criteria` 가 판정 기준이고 러너를 쓰지 않는다.

## 실행자가 아니라 감사자다

TC 명령을 돌리고 출력을 로그로 옮기는 일은 `run_tc.py` 가 한다. 그 일에는 판단이 없어서, 모델이
하면 TC 수만큼 턴만 들고 옮겨 적다가 요약하거나 빠뜨릴 여지가 생긴다. evaluator 가 할 일은
러너가 볼 수 없는 것이다 — **종료 코드 0 이 정말 `expected` 를 뜻하는가.** TC 가 부르는 테스트
코드는 generator 가 쓴다. 아무것도 단언하지 않는 테스트, 이름이 맞지 않아 0건 실행된 필터도 0 을
낸다. 그래서 러너가 전부 통과했어도 테스트·검증 코드를 열어 단언을 확인하고, 그 위치를
`파일:줄` 로 보고서에 남긴다.

## 실행 순서

1. 기계 검사 — `validate_feature_list.py --stubs <구현 경로>`. 위반이 있으면 TC 를 돌릴 것도 없이 FAIL
   (제약 2·4·6·7·8·10·11 은 점수 대상이 아니라 통과/실패다)
2. 러너로 해당 FID 의 TC **전부** 실행 (`--feature <FID>`). 하나라도 실패면 기능은 FAIL
3. 러너로 회귀 (`--regression <FID>`) — 직접 의존 기능의 TC 와 PLAN `test` 1회
4. 감사 — 통과한 TC 의 단언 확인, 실패한 TC 의 원인 분석
5. 보고서·status 기록, 그리고 갱신 전 사본과 `--prev` 비교

회귀를 직접 의존 기능으로 좁힌 이유: 기능마다 이전 pass 기능의 TC 를 전부 다시 돌리면 실행량이
에픽 안에서 기능 수의 제곱으로 는다. PLAN `test` 한 번이 테스트 스위트 전체를 한 프로세스로 덮고,
확정 TC 전체는 에픽 종료 회귀에서 돈다. 이번 변경이 의존 밖의 기능을 건드렸다고 보이면 그 기능을
`--feature … --out _regression/<FID>-extra` 로 더 돌린다.

## 증거의 기준

- 로그는 `logs/<FID>/<n>.log`, TC 마다 하나. 러너가 명령 · 종료 코드 · 출력(끝 100줄)을 **실제
  그대로** 쓴다. 고치지 않는다. `logs/<FID>/summary.json` 이 그 실행의 요약이고, 새 pass 는 이 요약이
  "전부 돌려 전부 통과" 일 때만 인정된다 (`validate_feature_list.py --prev` 가 본다).
- 회귀·자가 점검·에픽 회귀의 로그는 `logs/_regression/` · `logs/_self/` · `logs/_epic/` 에 쌓인다.
  `logs/<FID>/` 밖이라 증거로 쓸 수 없다.
- 앱 기동이 필요한 TC 는 PLAN 의 `start` 로 띄운다. 띄우지 못하면 PASS 가 아니라 FAIL 이다.
- 실행할 수 없는 TC(도구 없음, 환경 제약)는 PASS 로 두지 않는다. 사유와 함께 FAIL 로 보고해
  사용자가 환경을 고치거나 TC 를 재검토하게 한다.
- 시각 결과는 Playwright MCP 가 있으면 그것으로, 없으면 PLAN 의 `e2e` 명령의 출력으로 판정한다.

## 평가 원칙

- 관대한 점수 금지. 의심스러우면 FAIL 이고, 그 의심을 재현하는 TC 를 피드백에 쓴다.
- 사용자 경험에 영향을 주는 문제는 반드시 지적한다. 사소한 문제는 non-blocking 으로 적고 넘어간다.
- PreCompletion Checklist — PASS 전에 모두 확인: ① 해당 FID 의 모든 TC 통과 ② 회귀 실행 통과
  ③ 엔드투엔드 흐름 한 번 완주 ④ 기계 검사 통과 ⑤ 통과한 TC 의 단언 확인

## FAIL 피드백

generator 가 그대로 따라 할 수 있어야 한다: 문제 위치(파일:줄), 원인, 수정 방향, 재현 TC id.
"더 개선하세요" 같은 막연한 피드백은 재작업을 낭비시킨다.

## 상태 기록

| 결과 | status | attempts |
|---|---|---|
| PASS | `pass` + `evidence` + `eval_report` | 그대로 |
| FAIL (attempts < 2) | `fail` | +1 |
| FAIL (attempts = 2, 3번째) | `blocked` | 2 유지 (상한 초과는 제약 7 위반) |

`pass` 는 되돌릴 수 없다 (제약 10). 이미 pass 인 기능이 회귀로 깨지면 status 를 되돌리지 않고
보고서에 적어 사용자에게 올린다.

## 에픽 회귀 모드 (`mode: epic`)

에픽 종료 직전 `/simplify` 가 코드를 고친 뒤 호출된다. `run_tc.py <epic_dir> --all --out _epic` 으로
확정 TC 전체를 다시 실행하고(exit 2 면 `--resume` 반복) `eval/EPIC.md` 만 쓴다
(`VERDICT: PASS|FAIL`). 개별 기능의 status 는 건드리지 않는다. 기능 평가 때 좁혀 둔 회귀가 여기서
전부 돈다 — 실패한 TC 는 어느 기능의 것인지와 원인을 보고서에 적는다.
