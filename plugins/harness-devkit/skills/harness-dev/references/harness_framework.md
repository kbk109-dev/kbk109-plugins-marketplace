# 5-Component Harness Framework

"더 똑똑한 모델이 아니라, 모델을 둘러싼 더 똑똑한 환경"을 구현하는 5가지 구조적 구성요소.
각 컴포넌트는 LLM의 구조적 실패 모드를 시스템 수준에서 해결한다.

---

## 1. Readable Environment (읽을 수 있는 환경)

**해결하는 실패**: 세션 간 상태 유지 실패

세션 시작 시 30초 이내에 프로젝트 현재 상태를 파악할 수 있어야 한다.

### 점진적 정보 공개 (Progressive Disclosure)

slug 폴더 구조가 이를 구현한다 (2.0 레이아웃):

| 파일                                          | 언제 읽는가        | 역할                          |
| --------------------------------------------- | ------------------ | ----------------------------- |
| `harness_state.py status` 출력                | 매 진입의 첫 동작  | 파일 상태에서 판정한 현재 단계 |
| `docs/harness/{slug}/PROGRESS.md`             | 항상               | 세션 간 인수인계 로그         |
| `docs/harness/{slug}/epics/{NN}/feature_list.json` | 에픽 작업 중  | 현재 상태 스냅샷              |
| `docs/harness/{slug}/PRD.md` · `PLAN.md`      | 필요 시            | 제품 요구사항 · 구현 계획     |
| `epics/{NN}/TC.md` · `eval/` · `logs/`        | 기능 구현·평가 시  | 확정 TC · 판정 · 증거         |

### 설계 원칙

- 하나의 거대한 파일에 모든 것을 담지 않음 — 컨텍스트 오염, 정보 노후화, 신호 대 잡음비 저하 방지
- "지금 어느 단계인가" 는 모델이 추론하지 않고 `harness_state.py` 가 파일 상태에서 판정한다 — 재진입마다 같은 답이 나와야 한다
- 승인 표지는 전부 파일이다 (frontmatter `status: approved`, `.criteria_lock.json`, `.tc_lock.json`, `CLOSED.md`)
- 각 파일은 "사람이 읽어도 5분 안에 이해할 수 있는" 수준이어야 한다

## 2. Task State Machine (작업 상태 기계)

**해결하는 실패**: 상태 손실, 일회성 욕심, 조기 완료

`feature_list.json`이 상태 머신 역할을 한다. 각 기능의 `status`는 명확한 전이 규칙을 따른다.

### 상태 정의

| 상태      | 의미                                     |
| --------- | ---------------------------------------- |
| `fail`    | 아직 통과하지 못함 (기본값)              |
| `pass`    | Evaluator 검증을 통과함                  |
| `blocked` | 2회 재시도 후에도 실패, 사용자 개입 필요 |

### 허용되는 전이

```
fail → pass     (Evaluator 검증 통과 시)
fail → blocked  (재시도 2회 소진 시)
blocked → fail  (사용자가 차단 해제 시)
```

### 금지되는 전이

- `pass → fail` — 한번 통과하면 유지 (회귀가 발견되면 새 이슈로 처리)
- `blocked → pass` — 곧장 갈 수 없다 (`blocked → fail` 을 거쳐 다시 증명)
- 어떤 상태 → `pending` — "pending"은 존재하지 않음

2.0 에서는 이 전이를 코드가 강제한다 — `_feature_list_rules.py` 의 `check_transition`(제약 10)이 디스크의
이전 파일과 비교한다. `pass` 는 evaluator 만 기록하고(제약 9) 증거 로그 없이는 성립하지 않는다(제약 11).

### 왜 "fail"이 기본값인가

"pending"은 "아직 시작하지 않음"이라는 중립적 톤. "fail"은 "아직 통과하지 못함"이라는 도전적 톤. 에이전트는 작업을 *완료*하는 것이 아니라 *통과를 증명*하는 것이다. 이 인지적 차이가 조기 완료 선언을 방지한다.

### acceptance_criteria의 역할

- 기계 판독 가능한 계약서로 취급
- 테스트로 작성할 수 있다면 테스트로 실행
- 수정이나 삭제는 절대 불가 (어려운 criteria는 사용자에게 에스컬레이션)

## 3. Verification Loop (검증 루프)

**해결하는 실패**: 조기 완료 편향

### 핵심 원칙

**코드 작성 완료 ≠ 기능 완료** — 코드를 작성한 동일 컨텍스트에서 자체 평가하면 "완료" 사전 확률이 이미 왜곡됨.

### 구조

```
TC 작성(tc-writer) → TC 검토·확정(tc-critic) → 잠금
                                 │
Generator(서브에이전트) 구현 → Evaluator(별개 서브에이전트)가 확정 TC 를 실앱에서 실행 → PASS/FAIL
                                                          │
                                              FAIL → 피드백 + 재작업 (최대 2회)
                                                          │
                                              여전히 FAIL → blocked → 사용자 에스컬레이션
```

문서 단계도 같은 구조다 — writer → 회의적 critic → 수정(최대 2라운드) → 사용자 승인.

### PreCompletion Checklist

Evaluator가 PASS를 선언하기 전 반드시 확인:

1. **확정 TC 전수 실행** — 해당 기능의 모든 TC 를 개별적으로 실행하고 로그를 남김
2. **회귀 없음** — 이전에 pass한 기능들이 여전히 동작
3. **End-to-end 흐름 검증** — 구현된 기능들이 사용자 관점에서 연결된 흐름으로 동작

### Reasoning Sandwich

추론 노력을 단계별로 차등 배분:

- **계획 단계**: 최대 노력 (꼼꼼한 분석, 전략 수립)
- **구현 단계**: 중간 노력 (코드 작성에 집중)
- **검증 단계**: 최대 노력 (코드가 작성되었다고 추론을 생략하지 않음)

## 4. Architecture Enforcement (아키텍처 강제)

**해결하는 실패**: 나쁜 패턴 복제, 기술 부채 확산

### 왜 필요한가

에이전트는 코드베이스의 모든 패턴을 복사한다 — 좋은 패턴뿐 아니라 나쁜 패턴도. 이는 버그가 아니라 LLM의 핵심 메커니즘이다. 따라서 아키텍처 규율은 첫 스프린트부터 강제해야 한다.

### Generator 구현 시 준수 규칙

- 일관된 네이밍 컨벤션 사용
- 단방향 종속성 흐름 유지
- 기존 프로젝트의 좋은 패턴을 따르되, 나쁜 패턴은 답습하지 않음
- acceptance_criteria에 명시된 품질 기준 준수

### Evaluator 검증 항목

- 코드 품질 점수 (0~10)로 아키텍처 준수 여부 평가
- 7점 미만이면 스프린트 실패 → 구조적 개선 후 재시도

---

## 5. Loop Detection (루프 감지)

**해결하는 실패**: 동일 접근 방식 무한 반복, 토큰 낭비

### 감지 기준

Generator가 동일 파일을 **5회 이상 수정**하면 루프로 간주한다.

### 대응 절차

1. 현재 접근 방식을 즉시 중단
2. 문제의 근본 원인을 재분석 (보통 잘못된 가정에서 비롯)
3. 완전히 다른 접근 방식을 시도
4. 2번의 접근 전환 후에도 실패 → 사용자에게 에스컬레이션

### 왜 실시간 감지인가

사후 분석("나중에 보니 루프였다")은 이미 토큰을 낭비한 뒤. 루프가 진행되는 동안 추론 관성을 깨뜨리는 것이 핵심이다.

### Ralph Loop Pattern (목표 재주입)

기능 작업을 시작할 때마다 목표를 명시적으로 재선언한다. 여러 기능에 걸쳐 작업하면 원래 목표가 점진적으로 변형되는 "목표 표류"가 발생한다. 이를 방지하기 위해:

1. 대상 기능 ID와 이름을 재선언
2. 각 기능의 acceptance_criteria를 feature_list.json에서 원문 복사
3. 직전 Evaluator 피드백 요약 (있는 경우)

이 선언은 형식적 절차가 아니라 목표를 컨텍스트에 고정하는 기제이다. 2.0 에서는 `sprint_contracts/<FID>.md`
파일이 이 선언의 영속 형태다 — 새 세션의 evaluator 가 읽는다.
