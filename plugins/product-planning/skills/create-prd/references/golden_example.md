# 종단간 예제 — Journey-Forge 여행자 로그인

원문 "Mastering PRDs in Product Management" 이 직접 제시한 워크드 예시(Journey-Forge 의
Traveler Login & Registration)를 이 스킬의 플로우로 끝까지 실행한 기록이다.

아래 PRD 본문은 `validate_prd.py` 통과가 확인된 것이다. 형식이 의심스러울 때 이 문서를 기준으로 삼는다.

```
섹션 10/10 · US 3 · FR 4 · AC 4 · [제안] 2건(근거 확인 2건)
통과 — 모든 구조 검사 충족.
```

**게재된 PRD는 리뷰어 수정을 반영한 최종본(`revision_count: 1`)이다.** 초안이 아니다 — 초안을
예제로 실으면 이 문서를 참고하는 사람이 리뷰어가 이미 반려한 내용을 그대로 베낀다.
초안에서 무엇이 어떻게 고쳐졌는지는 아래 Step 7 에 적었다.

````markdown
# PRD — 여행자 로그인·회원가입

## 1. 문서 정보 (Document Information)

| 항목 | 값 |
| --- | --- |
| 기능명 | 여행자 로그인·회원가입 (Traveler Login & Registration) |
| 작성자 | kbk109 |
| 작성일 | 2026-07-30 |
| 버전 | 1.0 |
| 상태 | reviewed |
| 원본 문서 | Journey-Forge 기획 노트 |

## 2. 개요 (Overview)

**요약** — 여행자가 계정을 만들고 안전하게 로그인해 예약을 관리할 수 있게 한다.

**배경** — 현재 비회원 예약만 가능해 여행자가 지난 예약을 다시 확인할 방법이 없다.
고객 문의의 다수가 "내 예약 어디서 보나요"에 해당한다.

**목표** — 여행자가 스스로 예약 이력을 조회·관리할 수 있는 상태에 도달한다.
로그인 기능 자체가 목표가 아니라, 예약 관리의 자기 해결이 목표다.

**범위 밖 (Out of Scope)** — 소셜 로그인(구글·애플), 2단계 인증, 운영사 계정.

## 3. 유저스토리 (User Stories)

- **US-1**: As a 여행자, I want 이메일로 계정을 만들고 싶다 so that 예약 이력을 한곳에서 볼 수 있다.
- **US-2**: As a 여행자, I want 비밀번호를 잊어도 스스로 재설정하고 싶다 so that 고객센터를 기다리지 않아도 된다.
- **US-3**: As a 재방문 여행자, I want 빠르게 로그인하고 싶다 so that 번거로움 없이 여행을 계획할 수 있다.

## 4. 기능 요구사항 (Functional Requirements)

| ID | 요구사항 | 관련 스토리 |
| --- | --- | --- |
| FR-1 | 이메일과 비밀번호로 회원가입한다 | US-1 |
| FR-2 | 이메일 인증 링크를 통해 비밀번호를 재설정한다 | US-2 |
| FR-3 | 등록된 이메일·비밀번호로 로그인한다 | US-3 |
| FR-4 | 이미 사용 중인 이메일로는 가입할 수 없다 | US-1 |

## 5. 비기능 요구사항 (Non-Functional Requirements)

| ID | 요구사항 | 분류 |
| --- | --- | --- |
| NFR-1 | 비밀번호는 평문으로 저장되지 않는다 | security |
| NFR-2 | 로그인 응답이 2초 이내에 완료된다 | speed |
| NFR-3 | 인증 서비스 가동률 99% 이상 | scalability |

## 6. 유저 플로우 (User Flow / Journey)

1. 여행자가 로그인 화면에서 "계정 만들기"를 선택한다.
2. 이메일·비밀번호를 입력하고 제출한다.
3. 인증 메일을 받아 링크를 누른다.
4. 로그인 화면으로 돌아와 로그인한다.
5. 예약 관리 화면에 도착한다.

비밀번호를 잊은 경우 2단계에서 "비밀번호 찾기"로 분기해 3단계와 같은 메일 인증 경로를 탄다.

4단계에서 이메일·비밀번호가 일치하지 않으면 오류 안내와 함께 같은 화면에 머물러 재입력할 수 있고,
"비밀번호 찾기"로 이동할 수 있다. 인증을 마치지 않은 계정으로 로그인하면 인증 메일 재발송을 안내한다.

## 7. 수용기준 (Acceptance Criteria)

- **AC-1** (FR-1): Given 가입되지 않은 이메일을 입력한 상태에서, When 회원가입을 제출하면, Then 인증 메일 발송 안내가 표시된다.
- **AC-2** (FR-2): Given 가입된 이메일로 재설정을 요청한 상태에서, When 메일의 링크를 열면, Then 새 비밀번호 입력 화면이 표시된다.
- **AC-3** (FR-3): Given 인증을 완료한 계정이 있을 때, When 올바른 이메일·비밀번호로 로그인하면, Then 예약 관리 화면으로 이동한다.
- **AC-4** (FR-4): Given 이미 가입된 이메일이 있을 때, When 같은 이메일로 가입을 제출하면, Then "이미 사용 중인 이메일" 오류가 표시되고 계정이 생성되지 않는다.

## 8. 의존성 (Dependencies)

| ID | 의존 대상 | 사유 |
| --- | --- | --- |
| DEP-1 | 트랜잭션 메일 발송 채널 | 가입·재설정 인증 메일 발송에 필요 |
| DEP-2 | 예약 조회 API | 로그인 후 예약 관리 화면이 소비 |

## 9. 위험·가정 (Risks & Assumptions)

| ID | 내용 | 구분 |
| --- | --- | --- |
| RISK-1 | 인증 메일이 스팸으로 분류되면 가입 완료율이 떨어진다 | 위험 |
| RISK-2 | 기존 비회원 예약을 새 계정에 연결하는 방법이 정해지지 않았다 | 위험 |
| ASM-1 | 여행자 대다수가 본인 이메일에 즉시 접근할 수 있다고 가정한다 | 가정 |

## 10. 성공 지표 (Success Metrics)

| ID | 지표 | 목표 | 근거 |
| --- | --- | --- | --- |
| M-1 | 로그인 성공률 | 여행자의 90%가 2분 이내 로그인 | 원본 기획 노트에 명시된 합의 수치 |
| M-2 | 가입 이탈률 | [제안] 30% 이하 | 메일 인증 단계가 있는 가입 플로우의 통상 이탈 구간을 기준으로 한 초안 — 팀 확정 필요 |
| M-3 | 예약 문의 감소 | [제안] 문의 태그 `예약조회` 건수 20% 감소 (출시 후 4주 vs 직전 4주) | 배경에 적힌 "내 예약 어디서 보나요" 문의가 자기 해결로 대체된다는 가정 기반 초안. 측정 대상을 문의 태그로 한정 — 팀 확정 필요 |
````

**M-1 에 `[제안]` 이 없는 이유** — 원본 문서에 있던 수치다. M-2·M-3 은 모델이 만든 초안이므로
표기하고 근거를 적었다. 이 구분이 흐려지면 사용자는 무엇이 합의된 수치인지 알 수 없다.

## Step 7 — 리뷰어 3개 병렬

Task 도구 3개를 한 메시지에서 동시 호출했다. 실제 findings:

| 리뷰어 | verdict | findings |
| --- | --- | --- |
| design | `revise` | **D-1** blocking, 섹션 6: 4단계 로그인 실패 경로 없음 → 플로우 단절 |
| engineering | `pass` | **E-1** advisory, DEP-1: 메일 채널의 발송 한도가 가입 급증 시 병목일 수 있음 |
| qa | `revise` | **Q-1** blocking, M-3: "문의 20% 감소" 는 문의 분류 기준이 없으면 측정 불가 |

blocking 2건 → Step 6 로 복귀. 1회차 수정 — **위에 게재한 PRD는 이 수정이 반영된 상태다**:

| finding | 초안 | 수정 후 |
| --- | --- | --- |
| D-1 | 섹션 6 에 성공 경로만 있었다 | 4단계 로그인 실패 시 재입력·비밀번호 찾기·미인증 계정 분기를 추가 |
| Q-1 | `[제안] 문의 20% 감소` — 무엇을 세는지 없음 | 측정 대상을 문의 태그 `예약조회` 로 한정하고 비교 기간(출시 후 4주 vs 직전 4주)을 명시 |

Q-1 이 blocking 인 이유 — 지표에 수치가 있어도 무엇을 세는지 정의되지 않으면 출시 후에 달성 여부를
판정할 수 없다. `[제안]` 표기는 수정 후에도 유지된다. 측정 방법이 확정된 것과 목표치가 팀에
합의된 것은 다른 문제다.

2회차 리뷰에서 3개 모두 `pass`. `revision_count: 1`.
