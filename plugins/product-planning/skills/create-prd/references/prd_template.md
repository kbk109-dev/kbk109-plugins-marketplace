# PRD 템플릿 — 10개 핵심 섹션

원문 "Mastering PRDs in Product Management" 의 *10 key sections in a PRD* 표를 그대로 구조화한 것이다.
`docs/plan/PRD-{slug}.md` 는 이 형식을 따른다. `validate_prd.py` 가 이 형식을 전제로 검사하므로
**섹션 번호·한국어 제목·ID 접두어를 바꾸면 게이트가 깨진다.**

---

## 형식 계약 (validate_prd.py 가 검사하는 것)

| 규칙 | 이유 |
| --- | --- |
| `## {1..10}. {한국어 제목} ({English})` 10개 전부 존재, 본문 비지 않음 | 원문 10개 섹션 |
| 유저스토리는 `US-n` + `As a ... I want ... so that ...` | 원문 Step 3 이 지정한 형식 |
| 기능 요구사항은 `FR-n`, 비기능은 `NFR-n` | 원문 Step 4 의 functional/non-functional 분리 |
| 모든 `FR-n` 이 최소 1개 `AC-n` 에서 참조됨 | 원문 Step 5 + 흔한 실수 ③ |
| 모든 `AC-n` 에 Given·When·Then 세 키워드 존재 | 원문 Step 5 |
| `[제안]` 수치는 `근거` 컬럼이 있는 표 안에만, 근거 비지 않음 | 근거 없는 초안 수치는 날조와 구별 불가 |
| `TBD`/`TODO`/`작성 필요` 등 스텁 표현 0건 | 미완성 문서가 합의된 것처럼 유통되는 것 방지 |

`Given`·`When`·`Then` 키워드는 영어로 유지한다. 원문이 지정한 형식이고, 문서 간 검색·grep 이
가능해야 한다. 키워드 안쪽 내용은 한국어로 쓴다.

## `[제안]` 표기 규칙

원본 문서에 없는 수치를 모델이 업계 관행으로 초안 제안할 때만 쓴다.

- 원본 문서에 있는 수치 → 표기 없음. `근거` 에 출처를 적는다.
- 모델이 만든 초안 → `[제안]` 접두 + `근거` 에 **왜 그 수치인지** 적는다.

`근거` 가 "업계 표준"처럼 내용 없는 문장이면 QA 리뷰어가 반려한다. 무엇을 근거로 삼았는지
(원본 문서의 어느 서술, 어떤 플로우 특성) 를 구체적으로 적는다.

## 쓰지 말아야 할 것

원문의 핵심 원칙 — **"PRD는 의도를 설명해야 하며, 기술 명세서 역할을 해서는 안 된다."**
"어떻게 만들지"는 엔지니어의 몫이다. 명세로 취급하면 구현 여지를 없앤다.

| 금지 | 대신 |
| --- | --- |
| 테이블 스키마·컬럼 타입 | "이메일은 중복될 수 없다" (FR) |
| 함수·컴포넌트·파일 경로 | 사용자가 보는 동작 |
| 라이브러리 선정 | 만족해야 할 기준 (NFR) |
| 상태 관리 방식·아키텍처 결정 | 유저 플로우 |

경계 사례 — 원문 예시는 비기능 요구사항에 `bcrypt encryption` 을 적었다. 특정 알고리즘 지정은
구현 선택에 가깝다. 이 템플릿은 `NFR-1: 비밀번호는 평문으로 저장되지 않는다` 처럼 **만족해야 할
성질**로 쓰기를 권한다. 보안 정책·규정 준수로 알고리즘이 이미 정해진 경우에만 이름을 적고,
그 사유를 `근거` 나 `사유` 에 남긴다.
