# 리뷰어 공통 계약 — design / engineering / qa

원문 Step 6 은 *"PRD는 혼자 작성하는 것이 아닙니다. 초안을 디자인·엔지니어링·QA 팀과 일찍
공유하세요"* 라고 지시한다. 이 계약은 그 문장을 실행 가능한 형태로 옮긴 것이다.

## 왜 별개 서브에이전트 3개인가

PRD를 쓴 주체가 자기 PRD를 검토하면 통과시킨다. CLAUDE.md 의 실패 모드 표에서 **자기평가 편향**
항목이 정확히 이 현상이고, 저장소 규약은 *"검증을 생성과 같은 컨텍스트에서 하면 자기평가 편향이
발동하므로 별개 서브에이전트로 분리"* 하도록 정한다. 원문의 "혼자 쓰지 말라"와 저장소의
"생성자와 검증자를 분리하라"는 같은 요구다.

3개를 **한 메시지에서 동시 호출**한다. 순차 실행하면 뒤의 리뷰어가 앞의 지적을 보고 그 프레임에
갇혀 상관된 맹점이 생긴다. 서로의 결과를 모르는 상태가 이 설계의 값어치다.

각 리뷰어는 **담당 영역 밖은 침묵한다.** 세 리뷰어가 같은 지적을 반복하면 3개로 나눈 의미가
사라지고, 사용자는 중복된 목록을 읽느라 진짜 문제를 놓친다.

## 입력 컨텍스트

호출 시 아래 JSON 을 프롬프트에 담아 전달한다.

| 키 | 의미 |
| --- | --- |
| `prd_path` | 검토 대상 `docs/plan/PRD-{slug}.md` 절대 경로 |
| `source_excerpt` | 원본 문서에서 추출한 내용 (리뷰어가 "원본에 없는 내용"을 판별하는 기준) |
| `evidence_log` | 이 리뷰어가 근거를 기록할 로그 파일 경로 — `docs/plan/logs/review/{role}.log` |
| `revision_count` | 현재 수정 회차 (0부터). 3 이상이면 루프 가드가 곧 발동한다는 신호 |

리뷰어는 `prd_path` 를 **직접 읽는다.** 호출자가 요약해 준 내용을 믿지 않는다 — 요약 단계에서
문제가 이미 걸러졌을 수 있고, 그러면 검토가 무의미해진다.

## 출력 계약

마지막 메시지에 아래 JSON 을 포함한다.

```json
{
  "role": "design | engineering | qa",
  "verdict": "revise",
  "findings": [
    {
      "id": "D-1",
      "severity": "blocking",
      "target": "US-2",
      "problem": "무엇이 왜 문제인지 한 문장",
      "suggestion": "어떻게 고치면 되는지 한 문장"
    }
  ],
  "evidence_log": "docs/plan/logs/review/design.log"
}
```

### verdict

**기본값은 `revise` 다.** `pass` 는 blocking findings 가 0건임을 확인한 뒤에만 쓴다. "아직 통과를
증명하지 못한 상태"를 기본값으로 두는 것은 이 저장소 전반의 규칙이며, 조기 완료 선언을 막는다.

| verdict | 조건 |
| --- | --- |
| `pass` | `severity: blocking` findings 0건. advisory 는 있어도 된다 |
| `revise` | blocking findings ≥ 1건 |

### severity

| 값 | 의미 | 스킬의 처리 |
| --- | --- | --- |
| `blocking` | 원문이 명시적으로 금지·요구한 사항 위반 | Step 2 로 복귀해 수정 |
| `advisory` | 개선 제안. 원문 위반은 아님 | 미리보기에 표시, 사용자 판단 |

`blocking` 을 남발하면 루프 가드(3회)에 걸려 사용자에게 에스컬레이션된다. 원문의 어느 규칙을
위반했는지 말할 수 없으면 `advisory` 다.

### findings 가 0건일 때

빈 배열 `[]` 과 `verdict: "pass"` 를 반환한다. 지적할 것이 없는데 억지로 만들지 않는다 —
없는 문제를 만들어내면 루프 가드를 헛돌린다.

## evidence 로그

`evidence_log` 경로에 검토 과정을 남긴다. 스킬의 게이트는 리뷰어의 자기보고가 아니라 **이 파일의
실재와 비공백**을 확인한다. "검토했음"만 적고 로그를 남기지 않은 경우를 잡기 위한 장치다.

형식은 자유 서술이되 아래를 포함한다:

```
role: design
prd: docs/plan/PRD-traveler-login.md
revision: 0

[읽은 범위]
- 섹션 3 유저스토리 US-1~US-3
- 섹션 6 유저 플로우 1~5단계

[판단]
- US-2: "비밀번호 재설정 기능을 제공한다" 는 기능 서술이다. 사용자가 무엇을
  원하는지·왜 원하는지가 없어 원문 Step 3 의 형식과 목적을 둘 다 벗어난다.
- 섹션 6: 4단계에서 5단계로 가는데 로그인 실패 경로가 없다. 플로우 단절.

[verdict] revise — blocking 2건
```

## 리뷰어가 하지 않는 것

- **PRD 파일을 직접 수정하지 않는다.** findings 만 반환한다. 리뷰어가 문서를 고치면 누가 무엇을
  바꿨는지 추적이 끊기고, 수정 주체와 검토 주체가 다시 합쳐진다.
- **`validate_prd.py` 가 이미 잡는 것을 중복 지적하지 않는다.** 섹션 누락·GWT 키워드 부재·스텁
  표현은 스크립트가 기계적으로 잡는다. 리뷰어는 스크립트가 판단할 수 없는 것 — 내용의 質 — 을 본다.
- **다른 리뷰어의 담당 섹션을 논평하지 않는다.**
- **원본 문서에 없는 사실을 추가 제안하지 않는다.** 누락을 지적하는 것은 담당이고, 내용을
  발명하는 것은 담당이 아니다.
