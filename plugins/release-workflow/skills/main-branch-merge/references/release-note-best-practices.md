# Release Note 작성 베스트 프랙티스

이 문서는 main-branch-merge 스킬이 Release Note를 생성할 때 참조하는 가이드라인이다.
Keep a Changelog (https://keepachangelog.com) 포맷을 기반으로 한다.

---

## 파일 구조

```markdown
# {버전명}

> 릴리스 날짜: {YYYY-MM-DD}

한줄 릴리스 요약 (사용자 관점에서 이 릴리스의 가장 큰 변화)

---

- **변경사항 제목**: 변경 내용 설명
  - 마이그레이션 가이드: 기존 `xxx` → 새로운 `yyy`로 변경

---

## ✨ Added (새로 추가된 기능)
```

## 작성 원칙

### 1. 사용자 관점으로 작성

**좋은 예:**

- "라이브러리에서 도서 표지가 잘려 보이던 문제를 수정했습니다"
- "카메라 촬영 후 OCR 처리 속도가 40% 향상되었습니다"

**나쁜 예:**

- "BookCard 컴포넌트의 aspectRatio prop 수정"
- "OCR 파이프라인의 buffer allocation 최적화"

개발자 용어가 필요한 경우 괄호 안에 보충 설명을 추가한다.

### 2. 각 항목은 독립적으로 이해 가능해야 함

- 다른 항목을 참조하지 않고도 이 변경이 무엇인지 알 수 있어야 한다
- 너무 짧으면 정보 부족, 너무 길면 가독성 저하 → 1~2문장이 적당

### 3. Task ID 매핑

Notion Tasks DB의 완료된 태스크를 릴리스 노트 항목에 매핑한다:

```markdown
- **카메라 모듈 개발** — 도서 표지 및 페이지 촬영 기능 (S1-1)
```

- Task ID는 괄호 안에 표시
- 하나의 릴리스 항목이 여러 태스크를 포함할 수 있음: `(S1-1, S1-2)`
- 태스크에 매핑되지 않는 변경사항도 포함 가능 (버그 수정, 리팩토링 등)

### 4. 그룹핑

같은 기능 영역의 변경사항은 하나의 항목으로 묶을 수 있다:

```markdown
## ✨ Added

- **도서 등록 및 라이브러리** — 도서 등록, 표지 촬영, 라이브러리 그리드/리스트 뷰 (S1-1, S1-3)
- **카메라 촬영 시스템** — 페이지 촬영, 배치 촬영, 촬영 리뷰 및 재정렬 (S1-1, S2-3)
```

## Semantic Versioning 연동

| 버전 구성     | 의미             | 릴리스 노트 초점                                        |
| ------------- | ---------------- | ------------------------------------------------------- |
| MAJOR (x.0.0) | Breaking Changes | ⚠️ Breaking Changes 섹션 필수, 마이그레이션 가이드 포함 |
| MINOR (0.x.0) | 새 기능 추가     | ✨ Added 섹션이 주요 내용                               |
| PATCH (0.0.x) | 버그 수정        | 🐛 Fixed 섹션이 주요 내용                               |

- MAJOR 릴리스는 Breaking Changes를 최상단에 배치
- MINOR 릴리스는 Added를 먼저, Changed/Fixed를 이후에 배치
- PATCH 릴리스는 Fixed 위주, 간결하게 작성

## Notion Tasks DB → 릴리스 노트 매핑 규칙

### Tasks DB 쿼리

Notion Tasks DB에서 `Done: __YES__`인 태스크를 Sprint별로 그룹핑하여 수집한다.

### 매핑 로직

```
Task의 성격을 분석하여 섹션 분류:
- "개발", "구현", "구축", "추가" → Added
- "수정", "변경", "업데이트" → Changed
- "버그", "수정", "fix" → Fixed
- "최적화", "성능" → Improved
- "제거", "삭제" → Removed
- "보안" → Security
```

- Description과 Acceptance Criteria를 참고하여 사용자 관점 설명 작성
- Task ID를 항목 끝에 표시

### 예시 매핑

**Notion Task:**

```
Task: 카메라 모듈 개발
Task ID: S1-1
Sprint: Sprint 1
Description: expo-camera를 활용한 도서 페이지 촬영 기능 개발
Done: __YES__
```

**릴리스 노트 항목:**

```markdown
- **카메라 촬영 시스템** — 도서 페이지를 촬영하고, 연속 촬영 모드로 여러 페이지를 빠르게 스캔할 수 있습니다 (S1-1)
```

## 이전 릴리스와의 일관성

같은 `docs/release/` 폴더에 이전 릴리스 파일이 있으면:

1. **헤더 형식** 통일 (# v1.0.0 vs # Release v1.0.0 등)
2. **섹션 이모지** 통일
3. **항목 스타일** 통일 (볼드 제목 + 대시 + 설명)
4. **언어** 통일 (한국어/영어)

이전 파일이 없으면 이 문서의 기본 포맷을 따른다.

## 첫 릴리스 (v0.x.0 또는 v1.0.0) 특화

첫 릴리스에서는:

1. **프로젝트 소개**를 릴리스 요약에 포함
2. 모든 기능이 "Added"에 해당
3. Sprint별로 그룹핑하여 개발 히스토리 반영 가능:

```markdown
## ✨ Added

### Foundation (Sprint 0)

- **개발 환경 구성** — Expo SDK 55, TypeScript strict mode, ESLint/Prettier 설정 (S0-1)
- **UI/UX 디자인 시스템** — 색상 토큰, 타이포그래피, 공통 컴포넌트 라이브러리 (S0-4)

### Core Features (Sprint 1-2)

- **카메라 & OCR** — 도서 페이지 촬영 및 ML Kit OCR 텍스트 추출 (S1-1, S1-2)
- **도서 라이브러리** — 도서 등록, 그리드/리스트 뷰, 도서 상세 (S1-3)
```

## 빈 섹션 처리

해당하는 변경사항이 없는 섹션은 **포함하지 않는다**.
예를 들어 Breaking Changes가 없으면 ⚠️ Breaking Changes 섹션 자체를 생략한다.
최소 하나의 섹션(보통 Added 또는 Fixed)은 반드시 존재해야 한다.
