# Git 브랜치 워크플로

이 저장소에서 일상 작업 요청을 받을 때 따르는 브랜치·커밋·머지 절차다.

## 1. 작업 시작 — 브랜치 분리

- `main`에서 직접 수정·구현하지 않는다.
- 작업 요청을 받으면 현재 브랜치를 확인한다.
  - `main`이면: `main` 최신 기준으로 새 브랜치를 만든 뒤 그 브랜치에서 작업한다.
  - 이미 관련 feature 브랜치에 있으면: 새 브랜치를 또 만들지 않고 그 브랜치에서 계속한다.
- 사용자가 "main에서 해"라고 명시한 경우만 예외.

## 2. 브랜치 이름

형식: `{영문접두사}/{한글-간단-설명}`

| 접두사 | 용도 |
|--------|------|
| `feat/` | 기능·규칙·문서 추가 |
| `fix/` | 버그·깨진 동작 수정 |
| `docs/` | 문서만 |
| `chore/` | 설정·검증·잡무 |
| `refactor/` | 동작 동일 리팩터 |
| `test/` | 테스트·eval |

- 설명은 짧게, 공백 대신 `-`.
- 예: `feat/브랜치-워크플로-규칙`, `fix/ga-plan-파일명-통일`

## 3. 커밋 게이트

- 작업이 끝나도 **절대 자동 커밋하지 않는다.**
- 변경 요약을 보여 주고 **커밋 여부를 확인**한다.
- 사용자가 승인한 뒤에만 커밋한다.
- 커밋 메시지: 영문 접두어 + 한글 설명 (기존 관례).
- 커밋 전 반드시: `bash scripts/validate-marketplace.sh`

## 4. main 머지

- 커밋 승인·완료 후에만 진행한다.
- `git checkout main` → `git merge --no-ff <feature-branch>`
- **push는 별도 승인 전까지 하지 않는다.**
- 로컬 feature 브랜치는 머지 후 삭제한다 (`git branch -d`).
- PR 생성은 사용자가 요청한 경우에만.

## 5. 스킬 예외

- `/release-workflow:main-branch-merge`, `release-impl` 등 스킬이 브랜치·커밋을 따로 규정하면 **그 스킬이 우선**한다. 이 규칙은 일상 작업 요청용이다.

> 이 규칙 본문은 `project-conventions` 플러그인의 템플릿을 이 저장소에 맞게 고친 것이다.
> 여기를 고친 뒤에는 `--sync-mdc` 로 `.cursor/rules/` 사본을 다시 맞춘다. 전체 재설치는
> 템플릿에서 다시 렌더하므로 위 세 줄의 저장소 고유 내용이 사라진다.
